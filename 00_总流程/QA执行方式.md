# QA 执行方式

QA 统一规定 Figma 原稿高还原比对、谁检查、何时检查和怎样反馈；Token、组件与结构等专项检查内容由对应规范提供。

## 一、分工

| 类型 | 执行方 | 内容 |
|---|---|---|
| 客观检查 | AI | Figma 原稿还原度、主流程完整性、边界定义、结构健壮性、Shopee Guideline 与组件合规 |
| 判断检查 | 用户 | 产品目标、业务语义、交互方向、视觉判断 |

**确认只需要用户一个人。** 不要求 PM 与设计师分别确认——用户的一次明确确认即视为通过。

AI 无法从现有材料验证的内容不得标记为“通过”。

## 二、Figma 原稿超高还原门禁

本门禁同时适用于 Step 2 粗方案 HTML、Step 3 细方案 Figma 和 Step 4 反馈修改。现有产品改造没有通过本门禁，不得交付。

### 1. 锁定比对基线

- 记录用户授权的精确 Figma 文件、页面或节点、目标视口尺寸和需要比对的状态。
- 截取或导出同一视口、同一缩放、同一业务数据与同一状态的原稿基线图；不得拿局部原稿与整页产出、不同尺寸或不同状态做模糊比较。
- 在比对前标出“本次允许变化区域”。除该区域及其必要的最小联动区域外，其余均视为未改区域。

### 2. 实现策略

**Step 2 粗方案 HTML —— 默认走原图底板路线。**

1. 从 Step 1 锁定的 Figma 节点导出**高清原图**作为未改区域的视觉底板。清晰度要求见下方「底板质量硬要求」。
2. 在底板之上，用真实 HTML/CSS 构建：本次允许变化的区域、新增控件、主流程需要的关键状态，以及连接主流程所需的命中层。
3. 命中层必须与底板上可见控件同尺寸同位置，并带可访问名称；不得错位、不得用一张静态图冒充不同状态。

底板路线是**默认选择**，不是失败兜底——粗方案要验证的是交互机制，不是 HTML 复刻精度。只有当本次改动会让页面整体重排（底板无法表达）时，才改为结构化复刻整页。

#### 底板质量硬要求

底板是整个画板的视觉地基，糊了整块就废了。以下为硬性要求，不满足即判不通过：

- **导出倍率 ≥ 2×**：`get_screenshot` 的 `maxDimension` 必须设到「目标视口宽度 × 2」以上（例如目标视口 1440，`maxDimension` 至少 2880）。默认值 1024 远远不够，**不得使用默认值**。
- **只能等比缩小，绝不放大**：底板在页面中以 1× 显示，实际像素是显示尺寸的 2 倍以上。任何把底板拉伸放大的做法直接判不通过。
- **100% 查看时文字和图标清晰可辨**：包括正文、表格内文字、次级标签、小图标。有任何一处发虚、锯齿、糊边，重新导出。
- **不得二次压缩**：不转 JPEG、不降质量参数、不经过任何有损重采样。
- **完整覆盖目标视口**：不得出现底板边缘露白、裁切不全、比例不符。
- **导出后必须实际查看确认**，不能只看导出成功就继续。导出返回的 `width`/`height` 要与 `original_width`/`original_height` 对照，确认没有被服务端降采样到低于 2×。

底板不清晰属于门禁 A 组红线（低清），必须重新导出，不接受"能看清大概"。

**Step 3 / Step 4 细方案 Figma —— 复制原节点，不用底板。**

复制原 Frame、组件实例、变量与素材，只修改允许变化区域。**细方案不得把整页截图当作最终可编辑 Figma。**

### 3. QA 作用域（重要）

**样式像素比对只针对“我们自己做出来的部分”；整屏内容完整性 QA 覆盖底板。** 底板不做无意义的样式像素差异，但底板中的空白图片槽、缺图、错图、低清、裁切和状态残缺仍必须检查并修复。

| 区域 | 是否做像素比对 | 判定标准 |
|---|---|---|
| 原图底板区域 | ❌ 不做样式像素比对；✅ 做内容完整性检查 | 它就是原图，样式比对无意义。但必须检查「底板质量硬要求」，并逐个确认可见图片槽位没有非设计意图的空白、缺图、错图、低清或错误裁切；发现后在底板上覆盖恢复 |
| 自绘的变化区域、新增控件、关键状态 | ✅ **严格比对** | 见下方通过标准 |
| 命中层 | ✅ 严格 | 与底板可见控件同位置同尺寸，无错位 |
| Figma 细方案全部区域 | ✅ 严格 | 未改区域因为是复制原节点，应完全一致 |

Token 门禁同理：**Token 清单核验只针对自绘区域和新增交互层**，底板区域不参与 token 核验（它是位图，没有 token）。

### 4. 强制比对方式

每次生成或修改后，对**自绘区域**至少完成以下三项：

1. 原稿与产出同尺寸并排检查。
2. 以 50% 透明度叠加检查区域边界、位置、尺寸、文字基线、图标和素材。
3. 能力可用时生成像素差异图；不可用时放大到 100%–200% 逐区检查，并保留截图证据。

QA 证据写入真实 Case，不回写源模板；默认不向用户展开。

### 4.2 自检回执（落盘，不进聊天）

每次出图或修改后，把自检结果**追加**写入 Case 根目录的 `_自检回执.md`。**聊天里一个字都不提**——交付仍然只有链接、一句推荐和下一步。

回执必须写具体值，不能写"已检查""均通过"这类无法证伪的话：

```text
## 2026-08-09 14:32 ｜ Step 2 第 1 轮

Token 读取      Figma node 1:2，8 组全覆盖（Base/Neutral/Brand/Radius/Size/Space/Typography+TextStyles/Shadow）
本次 token      colorText, colorTextSecondary, colorBorder, colorBgContainer, sizeLG, sizeSM, Heading/s, Body/regular, borderRadius, boxShadow（10 项）
底板            2880×1620，2.0×，original 2880×1620 未降采样，已实际查看确认清晰

机械检查        文字溢出 0｜图片比例 0｜可访问名称 0｜画板文件数 1 ✓

```

**没做的项写 ✗ 并写原因，不留空、不写"N/A"。** 回执写不出具体值就说明这一步没真做，按未通过处理。

### 4.1 图片完整性硬门禁

截图对比不能替代图片加载检查。每次粗方案和 Figma 细方案 QA 都必须执行以下步骤：

1. 按“方案 × 关键状态”建立可见图片槽位清单，记录位置、应有内容、来源与实际素材；底板中的图片槽同样计入。
2. 实际进入主流程的每个关键状态后逐屏检查，不能只检查入口页，也不能用前一状态的底图遮住新增层后直接判定通过。
3. HTML 中对每个 `<img>` 与 CSS 背景图验证请求成功；`<img>` 必须满足 `complete === true`、`naturalWidth > 0`、`naturalHeight > 0`。同时检查实际像素至少覆盖显示尺寸 2 倍、比例与裁切正确。
4. 图片缺失时必须先从当前 Figma 节点、相邻状态、组件实例或页面已有图片恢复并实际填入；仍没有时，根据商品标题和页面其他图片的品类与视觉语境选择合适近似图，必要时用 `agent-reach` 搜索公开电商素材。
5. 替代图填入后重新渲染该状态并保存截图，再从第 1 项复检。清单中存在任何未验证、空白或加载失败槽位时，QA 结论只能是“不通过”。

### 5. 通过标准

**A. 硬性红线——出现任意一条即不通过，不受任何像素容差保护**

- 元素重叠、遮挡：新增按钮、卡片、浮层压住既有文字、控件或图片。
- 错位：控件脱离所在容器、脱离对齐线、浮在不该出现的位置。
- 文字溢出容器、被截断、换行破碎。
- 断图、缺图、空白占位、素材加载失败状态。
- 图片比例失真、拉伸、低清、主体被裁掉。
- 布局塌陷或整体重排：新增内容把无关区域挤走。
- 底板与自绘层之间出现可见接缝、色差、错位或重影。

**任何一眼就能看出来的问题都属于本组，一律不通过。** 不允许用"误差在容差内"为这类问题辩护。

**B. 自绘区域的量化标准**

- 位置、宽高、间距、对齐、文字基线与原稿对应元素的误差 **≤ 2px**。
- 字体家族、字重、字号、行高、颜色、圆角、边框、阴影必须与原稿一致，且取值来自 L1 token。
- 新增元素与相邻既有元素的间距、对齐、字号层级、圆角和颜色，必须与页面同类元素保持一致——**视觉上要像是原本就在那儿的，而不是贴上去的**。

**C. 整体协调性**

- 视口尺寸、页面裁切、滚动位置和状态与原稿一致。
- 允许变化区域与上下文自然衔接，信息层级不被打乱。
- 未改区域（含底板）内容不得被删减、改写、替换或重新布局。

**D. 可忽略项**

- 浏览器、Figma 渲染或字体抗锯齿导致的**孤立**像素噪声。
- 连续边界、布局、字体或素材差异**不得**按抗锯齿放行。

任一项未通过就返回实现步骤修改，并从锁定基线重新比对。不得标注"接近""大致""基本符合"。

**回环上限：任何检查项都是三轮，A 组也不例外**，超过三轮继续循环只会空转且用户看不见。三轮未过时的处理按组区分：

- **A 组红线三轮未过 → 必须告诉用户**，一句话说清卡在哪、缺什么。带着一眼可见的破损交付等于浪费用户的走查时间。
- **B 组量化项三轮未过 → 按最优结果交付，回执记录实际偏差，不打扰用户。**

## 三、调用时机

### Step 1 需求与文案确认前

- 检查目标角色、市场和语言是否明确；买家与卖家不得共用未经区分的角色语气。市场需逐个列出，不得笼统写“东南亚”。
- 检查本次新增或修改区域的标题或说明、字段、操作、确认或预览、成功、失败和恢复文案是否可直接使用。
- 检查术语、语义和语气一致；不得保留占位文案、直译腔、含糊对象或没有行动指向的提示。内部术语不得出现在用户界面。
- 检查`产品逻辑`八项是否都有答案：触发、时机、频次、持续、撤下、范围、例外、冲突与优先级。缺一项就不算澄清完成。
- 检查`需要你决定`是否已清空，且其中每条原本都是编号问句；未清空不得进入 Step 2。
- 检查`关键假设`只包含 PM 已确认的判断，未确认的判断没有混进`现状`当事实。

### Step 2 粗方案交付前

- 使用 [`explore-interaction-directions`](../02_交互/explore-interaction-directions/SKILL.md) 检查方案是否真正发散。
- 使用 [`flow-rules.md`](../02_交互/explore-interaction-directions/references/flow-rules.md) 检查每个方案的主流程与边界定义。主流程覆盖可见入口、核心任务、预览或确认、返回或取消、成功、状态更新和再次进入；边界覆盖失败、恢复、加载、权限、数据变化和中断恢复。
- 检查只有一个简洁 HTML 画板，全部方案均在其中可切换或对比，且每个方案都已实际走通主流程。顶部只保留 Case 名称与 A/B/C 切换；左栏顺序必须为方案身份与 1 句核心机制、优点与缺点、推荐理由（仅推荐方案）、主流程、1 句体验说明与重置、边界情况。锁定的桌面评审视口中左栏全部内容无需滚动即可看完。右侧只保留当前步骤和产品画面。全部步骤中壳层结构、宽度与位置保持稳定。
- 检查每个方案只有 2 条关键优点和 1 条主要缺点；三个方案只标记一个推荐方案，推荐标记同时出现在 Tab 和左栏，且只有该方案用“产品满足度｜一句话”“交互优势｜一句话”两行短句说明推荐理由。非推荐方案不得显示空推荐区块或额外“不推荐理由”。
- 边界流程不默认做成交互，必须在左栏最下方只选优先级最高的 3 条，按 `情况｜系统处理` 简短标注，标题只写“边界情况”。
- 检查三个方案的**产品逻辑完全一致**：触发、时机、频次、持续、撤下、范围和例外不得因方案不同而变化，方案之间只允许交互方式不同。
- 检查画板已走通 `产品逻辑` 的状态变化，至少覆盖触发前、触发后和撤下后。
- 检查 Step 1 `未决问题` 中每一条都有处理结论，不得静默丢弃。
- 检查右侧产品页面之外只有一层浅色承托底，优先使用 `colorBgLayout`；不得出现深灰画布、双层底色、嵌套卡片容器、重复圆角边框或厚重阴影。页面应直接放在唯一承托底上。
- 检查画板没有实现、研究过程或 QA 元信息，包括“DESIGN LOOP · 粗方案”“Figma 原图基线”“1440 × 900”“还原策略”“原图底板”“自绘层”“命中层”“像素比对”“粗方案仅标注”“QA 通过”“Agent Reach”“Mobbin”“Token”等；研究与 QA 证据只留内部记录。
- 检查三个方案两两至少有 2 项本质机制差异；竞品研究只作为机制证据，不得把方案限制成轻微变体。
- 严格执行本文件「Figma 原稿超高还原门禁」。未改区域有任何肉眼可辨差异时返回实现，不得继续交付。
- 按页面完整性清单检查区域、文字、控件、图标、商品图和关键状态；禁止非设计意图的空白、缺图、错图、断图、低清、拉伸、错位、遮挡、裁切和文字溢出。
- 执行本文件「图片完整性硬门禁」，逐个状态、逐个图片槽位验证真实加载；“整张底板成功显示”不能替代此项，也不能作为图片完整的证据。
- 原始商品图缺失时检查恢复顺序和替代图质量：先当前 Figma 节点、相邻状态、组件实例或页面已有图片；仍没有时根据商品标题和画面其他图片选择合适近似图，必要时再搜索同款、同品牌同品类或视觉语境最接近的公开电商图。图片像素至少覆盖显示尺寸 2 倍并保持正确比例。
- **市场证据标记为「已连接」时**，在内部记录中检查每个方案的研究机制、真实来源和适用理由；无法对应时返回研究或发散阶段。**标记为「用户确认无证据」时本项不适用**，方案依据记为「现有页面 + 痛点反推」。研究信息默认不单独显示在画板，只有推荐结论必须依赖时才压缩进推荐理由。
- 检查 AI 推荐同时说明“产品满足度”和“交互优势”，并逐项回扣 Step 1；只谈视觉或个人偏好不得通过。

上述检查由 AI 内部完成。未通过时继续修改；通过后只交付 HTML 画板链接、一句推荐和用户下一步，不展示长篇 QA 报告。

### Step 3、Step 4 Figma 交付前

- **先做 Token 合规核验**：确认本轮已完整读取 L1 与 Figma `✅ Design Token 设计令牌` 页，并逐项比对实际产出中的颜色、字号或文本样式、间距、圆角、线宽、阴影、控件高度是否全部来自已记录 token。出现裸值、Base 层直引、非档位数值、手写阴影或用透明度模拟状态时判为不通过。未完成 Token 读取的产出直接作废，不进入后续检查。
- 使用 [`Shopee-guideline检查项.md`](../03_视觉/Shopee设计系统/L5_检查项/Shopee-guideline检查项.md) 的 B 组逐条核验 Token 与样式。
- 使用 [`结构健壮性检查项.md`](../03_视觉/develop-visual-solution/references/结构健壮性检查项.md)。
- 使用 [`Shopee-guideline检查项.md`](../03_视觉/Shopee设计系统/L5_检查项/Shopee-guideline检查项.md)。
- 使用 [`通用视觉规范.md`](../03_视觉/develop-visual-solution/references/通用视觉规范.md) 的交付前自查。
- 将用户提供的视觉规范、截图和反馈转成逐条验收矩阵，并保留精确尺寸、组件、Token、文案、位置和状态要求。
- 严格执行本文件「Figma 原稿超高还原门禁」；Step 3 比对原稿与细方案，Step 4 同时比对修改前与修改后，确保未反馈区域完全不变。
- 执行本文件「图片完整性硬门禁」；复制原 Frame 后仍要逐个状态确认图片填充和加载，原稿或复制结果中已有空白图片槽不能原样带入交付。
- 逐条记录验证证据；任一客观条目未通过时继续修改，不得输出定稿或声称“基本符合”。

客观项未通过时，AI 回到出图步骤修改，然后从第一项重新自检，持续循环，不进入人评。不得交付、不得标注「基本符合」、不得把未通过项当作已知问题交给用户判断。同一项连续三轮无法通过时才停下来说明卡点并请用户决定。

## 四、反馈格式

**用户只需要给三段**，一条一行：

```text
位置｜问题｜期望
```

**优先级由 AI 判定并补齐**，不要求用户填。判定口径：

- `P0` —— 阻断主流程、功能错误、明显视觉破损（重叠、溢出、断图）。
- `P1` —— 不阻断但影响理解或规范合规（层级错误、Token 用错、文案不符基线）。
- `P2` —— 优化建议、可延后项。

AI 把每条反馈补成 `编号｜位置｜问题｜期望｜优先级` 后进入核销。用户主动标了优先级就以用户的为准。每轮按编号核销，不重复编号。用户没按格式给反馈时由 AI 自行结构化，不要求用户重写。

## 五、修改规则

- 只修改反馈明确指出的区域。
- 未反馈区域保持不变，并通过同视口叠加或差异图证明没有产生非预期变化。
- 发现范围外问题时只提出，不直接修改。
- 反馈暴露上游决策问题时，返回对应步骤重新确认。

## 六、完成条件

- 客观检查全部通过。
- P0、P1 反馈清零。
- **用户确认**。不区分 PM 与设计师两个角色，一次用户确认即视为通过。
- 用户明确提供的视觉规范验收矩阵全部通过。
- Figma 原稿超高还原门禁通过；QA 证据已保存到真实 Case。
