# Design Loop 总流程与调用时机

## 一、Design Loop 规则

每一步进入下一步前，AI 必须按本步输出标准自检；未达到标准就在本步继续循环，达到后才能进入下一步。

每一步开始前，AI 必须按本步“强制调用”逐项执行。不得因已有上下文、已经熟悉文件或能力相似而跳过；任一必需项未成功调用，本步不得完成。

Product Design 是 Codex 环境的插件，**按 Step 0 的探测结果决定是否强制，不靠判断当前是不是 Codex**。Step 0 逐个探测 `ideate` / `image-to-code` / `audit`，把结果写进 Case 标记，三者独立判定、独立降级。

- **标记为可用的工作流 → 硬门槛**：对应环节每次出图必须成功调用，只读取 `product-design:index` 不算成功。调用失败时停止出图并提示：`Product Design 插件未成功调用，请 @Product Design 后让我继续本次出图。`
- **标记为不可用的工作流 → 软门槛**：跳过该环节，改用 Figma 读写 + Shopee 设计系统正常出图，在 `_自检回执.md` 记一笔，不阻塞、不反复重试。

每次生成或更新 HTML 画板、设计图片或 Figma 视觉稿后，必须在目标视口执行页面完整性 QA。非设计意图的空白、缺图、错图、断图、低清、拉伸、错位、遮挡、裁切、文字溢出、图标缺失或状态残缺全部修复并重检后才能交付。

每次粗方案 HTML 或细方案 Figma 生成、修改后，还必须执行 [`QA执行方式`](QA执行方式.md) 的「Figma 原稿超高还原门禁」：锁定同一节点、视口与状态，明确本次允许变化的区域，对原稿与产出执行并排、叠加或像素差异比对。未改区域出现肉眼可辨差异即判为不通过，继续修改并重检；不得以“粗方案”“接近”“基本符合”作为降级理由。

**Step 2 粗方案默认走原图底板路线**：从 Step 1 锁定的 Figma 节点导出原图作为未改区域底板，只在允许变化区域构建真实 HTML 交互层。**底板区域不做像素比对、不做 Token 核验；自绘区域按门禁严格 QA。** 细方案（Step 3 / Step 4）复制原 Figma Frame、组件实例与素材后做最小改动，不用底板、不重新搭建近似外壳。

**底板倍率分级**：粗方案 HTML 底板按目标视口 1× 导出（`pngScale=1`），只做交互评审、不做视觉还原；细方案 Figma 才按 ≥ 2× 高清导出（`maxDimension` ≥ 目标视口宽度 2 倍，100% 查看清晰）。两者不要混用。

还原门禁的红线是"不能有一眼就看出来的问题"：元素重叠遮挡、错位、文字溢出、断图、比例失真、布局重排、底板与自绘层接缝——出现任一条即不通过，且不受像素容差保护。自绘区域的量化容差为 ≤ 2px。

### 设计规范门禁（出图强制前置，不可跳过）

**本节是全包关于设计规范执行的唯一定义。其他文件只引用，不重复定义。**

任何生成、编辑、合成或更新设计稿的动作之前，必须先完成以下三步。任一步未完成，本次出图不得开始；已开始的必须停止并回到本节。

**第一步：完整读取 Token 层（强制，无例外）**

- 完整读取 [`L1_原子变量/README.md`](../03_视觉/Shopee设计系统/L1_原子变量/README.md)。
- 完整读取 Figma 中 `Seller Center Library` 的 `✅ Design Token 设计令牌` 页（node `1:2`），至少覆盖：Base 调色板、Neutral 与 Brand 语义色、Border Radius、Size、Space、Typography、Text Styles、Shadow。
- Figma 与 L1 文档不一致时以 Figma 为准，并当场更新 L1 或记录差异。
- **Token 层读取采用变更检测**（见「Token 使用规范」）：同一次连续执行中只读取一次并贯穿；进入新反馈轮次时，先检查 L1 README 的 git status / mtime 与 Figma library 变更信号，未变化则复用上一轮 Token 清单，变化才重新读取。不允许凭记忆编造值、不允许因为需求小而跳过、不允许降级。读取失败时停止出图并报出原因，不得先出图后补读。

**第二步：按需读取组件层与页面层**

- 顺序仍为 L4 现有页面 → L3 全局规范 → L2 组件索引 → 本次实际使用的组件文档。定骨架仍然从 L3/L4 出发，不用 Token 反推页面结构；Token 层的强制读取只保证取值正确，不改变骨架决策顺序。
- 组件文档或页面拆解缺失、过时、与 library 不一致时，按 [`L5 检查项`](../03_视觉/Shopee设计系统/L5_检查项/Shopee-guideline检查项.md) 的「未建组件降级规则」处理并登记。**降级只适用于组件层和页面层，不适用于 Token 层。**

**第三步：建立本次 Token 清单**

出图前在内部列出本次将要使用的全部 token：颜色、字号与文本样式、间距、圆角、线宽、阴影、控件高度。清单是第四步自检的比对基准，不向用户展示。

### 通用设计知识的使用边界

**本节是全包关于通用设计知识如何参与判断的唯一定义。**

优先级固定为三级，不可颠倒：

1. **Shopee 设计系统（L1–L5）有定义** → 用 Shopee，通用知识不参与判断。
2. **Shopee 留白** → 用 [`通用视觉规范`](../03_视觉/develop-visual-solution/references/通用视觉规范.md) 与 [`图表选型`](../03_视觉/develop-visual-solution/references/图表选型.md)。
3. **两者都没有** → 由 AI 依据通用设计判断，并在交付时用一句话说明依据。

**Shopee 未覆盖的部分必须补足，不能因为"规范里没写"就跳过或随意处理。** 发现规范留白且反复出现时，记录下来作为 Shopee 设计系统的补充需求。

`frontend-design` **不在任何一步强制读取**，也不在包内保留——它的写作原则已全部内化到 `clarify-product-requirement` 的文案澄清和 `通用视觉规范` §六，读原文属于重复；且其色彩自选、字体配对、aesthetic risk、signature element、hero 主张、动效编排和移动端响应式等主张与项目当前的 Token 锁定、组件库锁定直接冲突，读进来只会污染判断。**范围说明**：本包视觉规范以 Seller Centre Web（桌面 Web）为当前基准；Seller APP / Shopee APP 等移动端按各自对应设计规范执行。

### 交付前自检与回环

交付给用户之前，AI 必须自行完成一轮规范自检，逐项比对上一步的 Token 清单与实际产出，并执行 [`L5 检查项`](../03_视觉/Shopee设计系统/L5_检查项/Shopee-guideline检查项.md)、[`结构健壮性检查项`](../03_视觉/develop-visual-solution/references/结构健壮性检查项.md) 与页面完整性检查。

- 任一客观项未通过：**回到出图步骤修改，重新自检，继续循环**。不交付、不标注"基本符合"、不把未通过项写成已知问题交给用户判断。
- **回环上限一律三轮**，A 组红线也不例外。三轮未过时：A 组红线必须告诉用户；B 组量化项按最优结果交付并在回执记录偏差，不打扰用户。
- 自检结果**追加写入 Case 根目录的 `_自检回执.md`**（格式见 [`QA执行方式`](QA执行方式.md) 4.2），**聊天里不提**。交付仍只有链接、一句推荐和下一步。

**只在以下三类情况打扰用户，各一句话，不展开：**

1. **我改不动** —— A 组红线三轮未过。例：`商品图三轮未能恢复，缺 SKU 12345 的可信图源，请提供或允许用同品类近似图。`
2. **需要用户拍板** —— 语义或交互层面的冲突。例：`你要的"提交后直接发布"会跳过 Step 2 已确认的预览环节，确认改吗？`
3. **需要用户提供东西** —— Figma 权限、Python 安装、插件安装、素材。

除此之外一律自己改完再交付。**数值类冲突不打扰用户**：用户要求的数值不在 token 档位时，取最近档位并在回执记录（例：要求 14px → 取 `sizeSM` 12 或 `size` 16）。**语义/交互类冲突必须问**：改变步骤、入口、业务规则或已确认文案含义的，不得自行取舍。

### Token 使用规范

**本节是全包关于读取与 token 成本控制的唯一定义。** 目标是：不读不需要的东西、不重复读没变的东西、不输出没人要看的东西。底线不变——「输入达标才输出」的客观检查不得因省 token 而跳过。

**1. 变更检测重读（代替无条件重读）**
- 读过的本地文件再次需要时，先检查 git status / 文件 mtime：**未变化不重读**，沿用上一次读取结果；变化才重新读取。
- Figma 等外部资源：同一次连续执行内复用（见 Step 3B 快速交接）；跨新反馈轮次时按变更信号（用户反馈涉及、节点内容更新）决定是否重读。
- 唯一例外：客观门禁明确要求"每次强制读取"的项（如首次进入 Step 3B 的设计规范门禁），按门禁执行。

**2. 读取分级**
- 小规范（L5 检查项、通用视觉规范、图表选型、视觉预期卡等）按需必读。
- 大文件（L1 README 366 行、组件索引等）先确认本次是否需要，按变更检测复用，不整篇无条件重读。
- 读取前先看文件大小/行数，超大目录用精确路径定位，不用递归 glob 扫全目录。`_建设参考`（组件建设资料）已移出包，不在包内读取范围内。

**3. 输出精简**
- 交付只包含：结果链接 + 一句推荐 + 下一步。自检明细、QA 过程、研究过程默认内化，写入 Case 内部记录，不向用户展开。
- 每轮正文按各 Skill 的字数上限执行（如 Step 1 每轮 ≤ 300 字）。

**4. 读取前自问**
- 每次要读文件前问一句"本次读取是否必要"：已有上下文能否覆盖？未变文件能否复用？只读需要的章节而不是整篇？答案是"可复用/不必要"时跳过。

**5. 唯一来源**
- 同一规则只在一个文件定义（模板目录、QA 执行方式、本节），其余只引用。引用时给路径，不复制内容。

### 自动化与用户操作边界

- 安装、工具发现、插件或 MCP 配置、连接发起、打开登录页、授权后复检、失败诊断与安全重试均由 AI 自动执行。
- 不得要求用户手动查找插件、复制命令、编辑配置文件、打开设置页或重复流程。
- 只有登录、OAuth 同意、权限批准、验证码、安全密钥或企业管理员审批等必须由本人完成的动作才暂停；AI 先把页面或系统弹窗打开到可操作状态，再用一句话说明用户当前只需完成的一个动作。
- 用户完成后，AI 自动继续并重新验证，不要求用户重复上下文或重新发起流程。

### 源包与真实 Case 边界

- `04_Case归档模板` 永久保留在 Design Loop 包内，作为只读源模板。
- 新需求进入 Step 1 前，由 AI 自动确保桌面存在 `Design Loop Cases/`，并把模板复制为 `Design Loop Cases/<Case名称>/`。
- Case 名称从已知需求生成简短、可识别且文件系统安全的名称；名称会影响理解时才询问用户，否则直接创建。
- 目标 Case 目录已存在时，不覆盖任何文件。确认是同一 Case 才续写；否则自动使用不冲突的名称，并在首次交付时告知实际目录。
- 需求总结、研究文字、HTML 画板、截图、Figma 链接、反馈记录与最终交付只写入该桌面 Case 目录。除用户明确要求维护源包外，不得把真实 Case 文件或运行产物写入 Design Loop 包。

### 用户引导与输出规则

- 面向用户的分析、研究结论、方案说明、画板注释、推荐理由、QA 阻塞说明和下一步默认使用简体中文。
- 页面内部面向目标市场买家或卖家的产品文案，继续使用 Step 1 已确认的目标市场与界面语言；不得把“页面文案用英文”扩展成“分析也用英文”。目标市场不限于东南亚，可能同时覆盖 BR、TW 等站点。
- 每一步开始时只用一句话说明：`当前步骤｜你需要做什么｜AI 接下来产出什么`。用户无需操作时明确说“你无需操作”。
- 只向用户追问会改变产品目标或硬约束的信息；其余研究问题、方案发散、QA 和检查由 AI 内化执行。
- 每一步只展示本步“输出”明确要求的内容，不展开研究过程、状态表、QA 清单或长篇澄清；除非存在阻塞或用户主动索取。
- 每一步结束时用一句话明确下一动作，例如“请确认需求总结”或“请在画板中选择方案 A/B/C”。
- **默认连续推进**：除三类必须打扰用户的情况外（我改不动 / 需要你拍板 / 需要你提供东西），AI 完成一步后自动进入下一步，**不需要用户说「继续」**；下一步无需用户操作时，一句话说明「我接下来自动完成 X，你无需操作」后直接执行。

## 三、主流程

### Step 0：安装准备包

**强制调用**

1. [`setup-design-loop`](setup-design-loop/SKILL.md)
2. 由 `setup-design-loop` 逐项检查并安装全部包内 Skill。
3. 由 AI 自动发现、安装、配置并连接 Product Design 插件、Figma、Mobbin、Agent Reach 和本地 HTML 预览能力。
4. 只有登录、OAuth、权限或安全验证必须由本人完成时才让用户点击；完成后 AI 自动继续并重新检查。

### Step 1：PM 需求澄清

**输入**

- 模糊的 PM 想法
- **节点级 Figma 链接（优先）**。改造现有产品给目标页面；全新项目给设计系统页、参考页或任意可作为视觉基线的节点。后续 Step 2 的粗方案和 Step 3 的细方案都以它为唯一视觉基线。
- **无链接降级（用户确认后可用）**：AI 必须先自动尝试连接、诊断和重试 Figma；确认仍无法取得或读取链接后，向用户确认是否用截图＋文字描述降级。用户同意后，Step 1 可依据截图、文字与 L4 同类页面拆解完成现状、产品逻辑和文案澄清，并将视觉基线标记为「待补」。**未补齐节点级 Figma 链接，不得进入 Step 2 生成 HTML 画板或 Step 3 输出 Figma 方案。**

**强制调用**

1. [`clarify-product-requirement`](../01_产品/clarify-product-requirement/SKILL.md)
2. 提供 Figma 链接时，调用 Figma 读取能力查看相关页面和状态。


**输出（PM 确认）**

- 现状
- 痛点
- 目标
- 预期方案
- 产品逻辑（触发、时机、频次、持续、撤下、范围、例外、冲突与优先级）
- 面向目标市场买家或卖家的文案基线
- 关键假设（只放 PM 已确认的判断）
- 需要你决定（未答完不得进入 Step 2）
- 未决问题

### Step 2：竞品调研与粗方案

**输入**

- Step 1 已确认的需求总结
- Step 1 已读取的节点级 Figma 链接与原始页面上下文；若 Step 1 使用无链接降级，必须先补齐并读取该链接，才能进入本步

**强制调用顺序**

1. [`research-market-solutions`](../02_交互/research-market-solutions/SKILL.md)
   - 强制调用 [`agent-reach`](../02_交互/agent-reach/SKILL.md) 与 Mobbin 完成市场调研。
   - 不下载或归档竞品图片；研究结论写入 Case 内部记录，作为方案机制约束与画板借鉴点来源（不占画板独立区块，格式见 `build-rough-prototypes` 固定画板格式）。
2. [`explore-interaction-directions`](../02_交互/explore-interaction-directions/SKILL.md)
   - 基于已确认需求、研究机制、当前项目机会和现有 Figma 上下文发散方案并检查链路。
3. [`build-rough-prototypes`](../02_交互/build-rough-prototypes/SKILL.md)
   - 强制调用 Figma 读取能力；Product Design 的 `ideate` / `image-to-code` / `audit` 按 Step 0 标记逐个执行（标记可用则必调且失败即停，标记不可用则跳过并在回执记录），再生成可点击 HTML。
   - 信息层级、布局密度、文案表达按 [`通用视觉规范`](../03_视觉/develop-visual-solution/references/通用视觉规范.md)；涉及图表按 [`图表选型`](../03_视觉/develop-visual-solution/references/图表选型.md)。本步不引入外部前端视觉主张。
   - 所有方案必须从 Step 1 的同一份 Figma 原稿基线开始，只改动方案所需区域，并放在同一个 HTML 画板中；未改区域必须通过「Figma 原稿超高还原门禁」。
   - 每个方案只强制实际走通主流程：可见入口、核心任务、预览或确认、返回或取消、成功与再次进入。边界流程完成内部定义后，在画板中以简短中文“边界情况”标注，不默认做成可点击状态；不得显示“粗方案仅标注”等流程元信息。
   - HTML 画板固定使用 `build-rough-prototypes` 的简洁评审格式：顶部只放 Case 名称和 A/B/C 切换；左栏只放方案身份与 1 句核心机制、2 条关键优点、1 条主要缺点、两行推荐理由（仅推荐方案）、主流程、1 句体验说明与重置、3 条纯文字边界情况，并在锁定的桌面评审视口中无需滚动即可看完。右侧只放当前步骤和产品画面；页面之外只允许一层浅色承托底，不得出现深灰内框、双层背景或额外卡片套层。全部主流程状态保持同一壳层，不得跳位。
   - 画板只显示方案判断和体验所需内容。不得显示“DESIGN LOOP · 粗方案”“Figma 原图基线”“1440 × 900”“还原策略”“原图底板”“自绘层”“命中层”“像素比对”“粗方案仅标注”“QA 通过”“Agent Reach”“Mobbin”“Token”等实现、研究过程或 QA 元信息。
   - 每次生成或修改画板后执行原稿还原 QA、主流程 QA、整屏页面完整性 QA 与图片完整性硬门禁；任一项未通过就继续修改。即使缺图已经存在于 Figma 截图底板中也必须恢复：先取 Figma 当前节点、相邻状态、组件实例或页面已有图片；仍没有时，根据标题和画面其他图片选择合适近似图，必要时用 `agent-reach` 搜索公开电商高清素材。
   - 三个方案两两至少有 2 项本质机制差异；推荐理由必须分别说明产品满足度和交互优势。

**输出**

- 1 个包含 3 个可点击方案的 HTML 画板
- 画板内用简体中文为每个方案显示 2 条关键优点和 1 条主要缺点，只标记一个推荐方案，并仅在该方案用两行短句显示“产品满足度”和“交互优势”；下方依次显示主流程、1 句体验说明与重置、3 条纯文字边界情况。研究证据、背景分析与当前项目机会全部保留在内部记录，不单独占画板区块；页面内部文案使用 Step 1 已确认的目标市场语言

**用户下一步**

- 在 HTML 画板中体验并选择方案，或指出要组合的部分。

### Step 3：选定方案、视觉澄清与视觉输出

#### Step 3A：选定方案与视觉澄清

**输入**

- Step 2 的 3 个粗方案

**强制调用**

1. [`develop-visual-solution`](../03_视觉/develop-visual-solution/SKILL.md) 的 Step 3A。
2. 完整读取 [`视觉预期卡`](../03_视觉/develop-visual-solution/references/视觉预期卡.md)。

**输出**

- 选定的粗方案
- 已锁定的视觉预期

**自动进入下一步**

- AI 用 1–2 句话复述用户选择的视觉预期后直接进入 Step 3B，不要求用户再次回复“确认”；用户有异议时可随时打断。

#### Step 3B：视觉方案输出

**输入**

- 选定的粗方案
- 已锁定的视觉预期

**强制调用顺序**

进入本步先做快速交接：仅核对选定方案、已锁定视觉预期、**Step 1 已确认的`产品逻辑`**、Step 1 原 Figma 节点和真实 Case 交付目录。五项齐全后立即开始，不再设置用户确认门槛；不得重新生成或精修粗方案、重复 Step 2 QA、制作独立中间视觉图，或把"归档方案"变成新的出图任务。选定粗方案只传递交互机制、主流程、信息层级和业务规则。

1. **设计规范门禁**（见上文「设计规范门禁」）：完整读取 [`L1_原子变量`](../03_视觉/Shopee设计系统/L1_原子变量/README.md) 与 Figma `✅ Design Token 设计令牌` 页（node `1:2`）。未完成不得进入后续任何一项。
2. [`develop-visual-solution`](../03_视觉/develop-visual-solution/SKILL.md)
3. 重新读取用户授权的原 Figma 目标节点，锁定要复制的 Frame、允许变化区域和可复用结构；选定粗方案只锁定交互机制、主流程、信息层级与业务规则，不作为视觉像素来源。
4. Product Design（仅当 Step 0 标记 `ideate` 可用）：先读取 `product-design:index` 路由，再调用 `product-design:ideate`；只读取入口不算完成。标记不可用时跳过。此调用只做内部承载检查，不生成需用户再次选择或需独立精修、独立 QA 的中间视觉稿。
5. Figma 读写能力：Product Design 环节完成后（可用则调用成功、不可用则已跳过）立即在 Figma 中复制原 Frame 并原生搭建，不先把粗方案做成一张完美图片再复刻。
6. 有对应页面时读取 [`L4_现有页面`](../03_视觉/Shopee设计系统/L4_现有页面/)
7. 读取 [`L3_全局规范`](../03_视觉/Shopee设计系统/L3_全局规范/全局规范.md) 定页面骨架
8. 读取 [`L2_组件索引`](../03_视觉/Shopee设计系统/L2_组件/组件索引.md)，再读取本次使用的组件文档
9. 读取 [`通用视觉规范`](../03_视觉/develop-visual-solution/references/通用视觉规范.md) 补 Shopee 留白；涉及图表时读取 [`图表选型`](../03_视觉/develop-visual-solution/references/图表选型.md)
10. 复制目标 Figma 原 Frame、组件实例与素材作为视觉基线，只修改选定方案必需区域；保持图层、组件、变量和布局原生可编辑，不得用 HTML 截图或整页位图交付
11. 出图前建立本次 Token 清单
12. 交付前执行「Figma 原稿超高还原门禁」「图片完整性硬门禁」、[`结构健壮性检查`](../03_视觉/develop-visual-solution/references/结构健壮性检查项.md) 与 [`L5 检查项`](../03_视觉/Shopee设计系统/L5_检查项/Shopee-guideline检查项.md)，未全部通过则回到 Figma 搭建继续循环

同一次连续 Step 3B 中，设计规范门禁只读取一次并供后续 Product Design、Figma 搭建和本轮 QA 共用；不得因能力切换重复读取。进入 Step 4 的新反馈轮次时再重新读取。

**输出**

- Figma 可交互原型

**用户下一步**

- 在原型中走查并按位置给反馈。

### Step 4：根据反馈修改至满意

**输入**

- 用户反馈
- 用户提供或已确认的视觉规范、截图、检查表和必须保持项

**强制调用顺序**

1. **设计规范门禁**：本轮涉及出图时，按「Token 使用规范」变更检测规则读取 [`L1_原子变量`](../03_视觉/Shopee设计系统/L1_原子变量/README.md) 与 Figma `✅ Design Token 设计令牌` 页——未变化则复用上一轮 Token 清单，变化才重新读取。
2. [`develop-visual-solution`](../03_视觉/develop-visual-solution/SKILL.md)
3. Product Design（按 Step 0 标记）：检查已有方案调用 `product-design:audit`；需要生成或更新视觉稿时再调用 `product-design:ideate`。每次出图都必须重新成功调用。
4. Figma 读写能力
5. [`QA执行方式`](QA执行方式.md)
6. 本次涉及的 Shopee Guideline、组件文档与 [`通用视觉规范`](../03_视觉/develop-visual-solution/references/通用视觉规范.md)
7. 在同一视口、同一状态对修改前原稿和修改后产出执行超高还原比对，未反馈区域出现差异时恢复原稿
8. 交付前自检，未通过则继续循环（见上文「交付前自检与回环」）

**输出**

- 客观规范全部通过后的 Figma 待确认链接
- 用户明确确认后的 Figma 定稿链接

**用户下一步**

- 确认是否定稿；未满意则继续按反馈修改。

每轮将视觉规范转为内部验收矩阵并逐条核验；任一客观要求未满足就继续修改，不输出定稿。所有客观要求通过且 用户明确确认后才完成。反馈按 P0/P1/P2 分级：P0 本轮必修，P1/P2 可累积；同一 Case 反馈修改最多 3 轮，超过 3 轮强制升级——AI 用一句话报告卡点，请用户决定重审需求（回 Step 1）、放宽标准或人工介入（见 [`QA执行方式`](QA执行方式.md) 五.1）。

## 四、能力边界

| 交界 | 上游交付 | 下游不得越权 |
|---|---|---|
| 产品 → 交互 | 已确认的现状、痛点、目标、预期方案、**产品逻辑**、目标角色与文案基线，以及关键假设和未决问题 | 交互阶段不得改写产品目标、产品逻辑或文案语义；**未决问题不得静默忽略**；发现问题时返回 Step 1 |
| 市场研究 → 方案发散 | 方案类型、证据、适用条件、当前项目机会 | 研究阶段不直接生成当前项目方案 |
| 交互 → 视觉 | 选定粗方案及完整链路，以及 Step 1 已确认的**产品逻辑** | 视觉阶段不得改变核心步骤、入口、业务规则或产品逻辑；出稿须覆盖触发前、触发后与撤下后状态 |
| 视觉澄清 → 视觉执行 | 用户已选择且 AI 已复述锁定的视觉预期 | 视觉执行不得重新解释视觉目标，也不得追加一次确认 |
| AI → 人 | 本步规定的精简交付与下一步指引 | AI 不替用户确认和拍板；自查明细默认内化 |

## 五、Case 归档

每个 Case 开始时，由 AI 把 [`04_Case归档模板`](../04_Case归档模板/) 复制到桌面独立根目录，执行过程中持续写入，完成后在原目录整理。默认位置：

```text
Desktop/
└── Design Loop Cases/
    └── Case名称/
```

Case 内结构：

```text
Case名称/
├── 01_需求澄清/
├── 02_竞品调研/
├── 03_粗方案/
├── 04_Figma/
└── 05_反馈/
```

`04_Case归档模板` 始终留在 Design Loop 包内且保持为模板；真实 Case 不得创建在源包目录或模板目录中。
