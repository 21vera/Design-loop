# PM 需求澄清

## 输入

- 模糊的 PM 想法
- **节点级 Figma 链接（必填，无一例外）**。改造现有产品时给目标页面；全新项目时给设计系统页、参考页或任意可作为视觉基线的节点。没有链接不进入 Step 1，只用一句话请用户提供。
- 可选：已有背景、数据、用户反馈或业务约束
- 可选：目标市场、语言、用户角色和已有术语表

## 强制调用

1. 调用本 Skill 完成需求澄清。
2. 调用 Figma 读取能力查看目标页面、入口、状态与约束。**Figma 链接是 Step 1 的硬前置**：后续 Step 2 的粗方案和 Step 3 的细方案都必须以它为唯一视觉基线，没有它整条 loop 走不下去。

本步不调用市场调研、交互、视觉或出图 Skill。Figma 无法读取时先自动诊断并恢复连接；只有登录、OAuth、文件权限或企业审批必须由本人完成时才让用户操作。连接仍不可用时再请求补充截图，不得跳过现状检查。

## 工作方式

1. 先读取与需求相关的页面、入口、主路径、当前状态和约束，用于理解现状，并记录本次的视觉基线节点（file key + node id + 目标视口）。
2. Figma 无法访问时，自动检查工具、连接、授权 scope、文件权限和限流并安全重试；需要本人身份或权限时，先自动打开对应页面，再只请求用户完成该动作。仍无法访问时才请求补充截图，不猜测现状。
3. **先查尽，再问**。Figma 里的入口、字段、状态、现有文案，以及 L4 同类页面拆解——能查到的一律自己查完。**只有查不到、且会改变现状、痛点、目标、目标角色、语言或硬约束的，才问 PM。** 事实自己找，判断才归 PM。
4. **问题一律确认式，不用开放式。** 带上你的推断和依据，让 PM 只需要确认或纠正一个词，不要让他从零组织答案。
   - ✅ `从页面看，这是东南亚卖家批量改价的场景，痛点是逐个改太慢。对吗？不对的话是哪一类？`
   - ❌ `目标用户是谁？` `你希望达到什么效果？`
5. 每轮只问一个问题；已有 Figma 和上下文足够时不继续追问。
6. **需求内部打架时必须挑明**——只挑会让方案分叉的那种，一句话说清两边，请 PM 定优先级，不展开分析。例：`「一眼注意到」和「不打扰」会把方案拉向两个方向，哪个优先？` 不挑明的矛盾会一路带进 Step 2 的三个方案，到 Step 4 才暴露。
7. 完成下方“文案澄清”，生成可直接放入界面的文案基线。
8. 信息足够后直接输出需求总结，等待 PM 明确确认。
9. PM 修改内容时，只更新受影响的部分，再次请求确认。
10. 面向 PM 的需求分析、解释和总结默认使用简体中文；`文案基线` 中实际放入页面的文案仍按目标市场与界面语言输出。不得因为产品界面使用英文，就把需求分析也改成英文。

## 文案澄清

1. 明确文案服务的用户角色：东南亚买家、东南亚卖家或两者；同时确认目标市场、界面语言和关键产品术语。能从 Figma 或上下文判断时直接采用，无法判断且会改变文案时只问一个问题。
2. 根据角色、任务与场景，写出本次新增或修改区域的生产可用文案，至少覆盖：标题或说明、字段标签与提示、主次操作、确认或预览、成功、失败与恢复。
3. 优先使用短句、动作开头、具体对象和明确结果。默认英文产品面向东南亚时使用简单自然的国际英语；不得直译中文表达、使用中国互联网黑话、含糊代词或无行动指向的口号。
4. 保持现有产品术语一致；同一对象、动作和状态只使用一个称呼。同一动作在按钮、过程状态和结果反馈中同名：按钮写 `Publish`，成功提示就写 `Published`。
5. 从用户这一侧命名，不按系统实现命名——用户管理的是「通知」不是「webhook 配置」。按钮写清点击后的结果（`Save changes`），不写模糊的 `Submit`。错误文案说清发生了什么和怎么解决，不道歉、不含糊；空状态给出下一步。
6. 不提前为三个交互方向分别写三套完整文案。先确认统一语义与基线，Step 2 只可因机制、空间或状态差异微调，不得改变已确认含义、语气和术语。
7. 本次确实不涉及用户可见文案时，在文案基线中明确写“无新增或修改文案”，不得省略该检查。

## 输出

严格使用以下结构，不增加方案建议、竞品判断或设计内容：

```markdown
# 需求总结

## 现状
- …

## 痛点
- …

## 目标
- …

## 预期方案
- …

## 文案基线
- 目标角色 / 市场 / 语言：…
- 关键术语：…
- 核心界面文案：…

确认：待 PM 确认
```

输出后只追加一句：`下一步：请确认或修改以上需求总结。`

`预期方案` 记录 PM 当前假设，不视为最终设计结论。`文案基线` 是 Step 2 的统一语义基线，可随选定方案微调表达但不可改变含义。

PM 明确确认后，将确认状态改为：

```text
确认：PM 已确认
```

## 边界

- 不搜索或评价竞品。
- 不生成交互方向、页面结构或粗原型。
- 不讨论颜色、组件、布局或视觉风格。
- 不写 PRD、设计 Spec、代码或实施计划。
- 信息不足时不替 PM 补写事实；将缺口转成一个**带推断的确认式问题**，而不是开放式问题。
- 不把可以自己查到的事实问给 PM。
- 不向用户展示 AI 的内部假设清单、分析过程或自检过程。

## Token 规则

- 不读取交互或视觉阶段的材料。
- 只读取 Figma 中与当前需求相关的页面和状态。
- 不复述完整对话，只保留已确认信息和当前未决问题。
- 不为五个输出项增加额外章节。
