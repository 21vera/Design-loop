## 🔴 十六条铁律（背下来再开干）

1. **🎨 Figma 先行原则**：**永远是 Figma 先做完整、设计师认可之后，才能写代码**。Phase 3-4（Token + 组件 + Display 排版）100% 完成 → 给用户/设计师 review → 拿到 OK → 才进 Phase 5。AI 不能擅自跳过 Phase 4 直接写代码，理由"设计师手动建"是过时的——AI 就是来辅助做这步的，**没人在画时 AI 必须顶上**。
2. **📐 Display 排版规范统一 (Property × Value Matrix)**：所有组件的 Figma 展示页 `{X} — Display` 必须严格按下方「📐 Display 排版统一规范」做 — **深色 Header + 单一 Property × Value 矩阵 + 全英文 + top-left + 不放 Scenarios**。每行 = 一个 prop, 列 = 该 prop 的所有 value, baseline 保持其它 prop default。Cell 必须 ComponentSet instance, **不准画裸图形**。详细见后面专节。
3. **🔒 Scope 契约不准跳过**：Phase 2.5 每个 prop 标 Tier 1/2/3/4 来源，Tier 4 必须用户书面签字才能加。
4. **📜 旧规范 + 旧 Vue 都有的状态/feature = Tier 1**，AI **不准**当成 Tier 4 让用户选 (Checkbox `indeterminate` 第一版犯过的错: 旧 Guidelines 明确画了, 旧 Vue 有 prop, 我却放到 AskUserQuestion 里给用户挑, 让本来必做的标准状态变成了可选项)。判定方法见下方「Tier 评级速查」。
5. **🔤 字体 Family 强制 Roboto, 字重看旧库**：
   - **Family 全局规则**: 做组件时全部用 **Roboto**, 不许用 Inter. 在 `module.css` 写 `font-family: 'Roboto', var(--fontFamily);`, Figma 用 `fontName: { family: 'Roboto', ... }`。
   - **字重不是全局规则**: **默认 Regular (400)**, **只有旧库 / 旧 Guidelines 明示 Medium 时才用 Medium (500)**。
   - **判定法**: Phase 1 时用 `get_design_context` 扒旧库的目标 component, 看返回的 `Font(... style: Regular/Medium, weight: 400/500 ...)` 字段, 抄那个。**不准凭"Tag 是 Medium 所以这个也是"脑补**。
   - 历史错误: Card title 应 18px Medium (旧库实际), 我用了 22px; Breadcrumb 应 16px Regular (旧库实际), 我用了 14px Medium。已修正。
6. **📏 精确数值看「旧组件库」优先于 System Test**：当 System Test 已有组件而尺寸看起来不对时, **必须回到旧库 (4EgWXbFDmKLRpU0hdZeDh4) 扒原始尺寸做对比**, 不要默认 System Test 是对的。Tag 第一版照搬 System Test 的 24px 高度, 实际旧库是 18px, 用户手动指出后才纠正。**判定法**: 用 `get_metadata` 扒旧库对应 frame, 看每个变体的 width/height, 这是终极依据。

   **6a. Phase 4 起手必修 — 旧组件库数值预提取**: 建 ComponentSet **之前**, 必须用 `use_figma` 写 `walk()` 把旧组件库目标 symbols 完整数值表 dump 出来, 包括下面 7 类:
   - **尺寸**: width / height / padding / itemSpacing / cornerRadius
   - **效果**: `effects` (drop shadow 通常 **2 层**: ambient y=0 + key y=offset, 不是 1 层)
   - **图标**: status icon / close icon 的实际 `width`/`height`/`x`/`y` (旧 Vue SCSS 不会写这些, 必须扒 Figma)
   - **字号 + 字重**: 每个 text 的 `fontSize` + `fontName.style` (Regular/Medium/Semi Bold)
   - **颜色**: 每个 fill 的实际 SOLID 值 (用 `rgb(r*255, g*255, b*255)` 推断 token)
   - **按钮**: 真实文案 ("Cancel" / "Confirm" / "OK"), 不是 placeholder "Button"; 按钮 Type/Size (Primary/Default/Small/Default)
   - **布局**: Status 类型是否 center-align, footer 按钮顺序, footer 是否含 footer-assist 槽

   **绝对禁止**: 凭旧 Vue SCSS 变量 (如 `$modal-shadow`) 估算 — SCSS 是手动维护的, 跟旧库 Figma 实际值经常不一致 (Modal v1 我用 SCSS shadow `0 1px 8px 0 rgba(0,0,0,0.12)`, 但旧库实际是 2 层 `radius 16 y=8 a=0.04` + `radius 16 y=0 a=0.10`)。

   **判定法**: Phase 4 开干前先跑这种脚本:
   ```js
   const node = await figma.getNodeByIdAsync('<旧库 ID>');
   await figma.setCurrentPageAsync(<parent page>);
   function walk(n, d=0, max=5) { /* dump 上述 7 类 */ }
   return walk(node);
   ```
   把 dump 结果对照 Token 表, 不对的地方先改 Token 再开始 ComponentSet。

   **6b. Figma 现有 Icon master 必须用 ID + getNodeByIdAsync 查, 不要 findAll**: Shopee Figma 文件里很多 icon master 是「孤儿 component」(`parent === null`, 创建时没挂到 page 上)。`findAll(n => n.type === 'COMPONENT')` **找不到孤儿**, 只能从 instance 反向找 `instance.mainComponent.id`, 然后 `getNodeByIdAsync(id)`。

   **判定法**: 找现有 Icon 的两步法:
   1. 找一个**已知用了该 icon 的 INSTANCE 节点** (旧组件库 / 旧 Guidelines / System Test 文档示例都行)
   2. 读 `instance.mainComponent.id` 拿到 master ID, 收到清单里
   3. 后续 `getNodeByIdAsync(id)` + `.createInstance()` 即可

   **历史教训**: Modal v1 我用 findAll 在 Icon page 上只找到 8 个 component, 以为 status icons 不存在, 自己用 `createNodeFromSvg` 创了 5 个重复 icon (close + success/error/warning/info)。其实旧库 40:595 「Section / Status」里 12 个 status icon (success-s / error-s / notice-triangle-s / information-s 等) 全部存在, 只是 parent=null。后来要全部清理 + 替换为现有 master, 双倍返工。
7. **🎨 引用 atomic token 名字必须先 grep 验证**: 写 `{X}.tokens.css` 时, 不准凭"应该是这样吧"假设 `--gray-3`、`--cyan-1` 这种名字, **必须先 grep `src/tokens/atomic.css` 看实际命名**。Tag 第一版用了 `var(--gray-3)` / `var(--cyan-1)`, 实际 atomic 用的是 `--neutral-3` / 没有 cyan, 导致背景色完全丢失。**判定法**: 写 Component 层 token 的 CSS 引用之前, 跑 `grep -E '^\\s*--{颜色名}' src/tokens/atomic.css` 验证, 拿到的才能用。命名对照: 灰=`neutral-1..10`(不是 gray), 蓝=`blue-1..10`, 黄=`yellow-1..10`, 绿=`green-1..10`, 橙=`orange-1..10`, 红=`red-1..10`, **没有 cyan/purple/pink 等其他色系**。

8. **♻️ 必须 instance 现有组件, 禁止重新画 / 自创外观**: 做新组件时, 凡是**视觉上等价于已建好的组件**(Button / Icon / Avatar / Badge / Breadcrumb / Tag / ...) 的部分, **必须直接 instance / import 现有 ComponentSet**, 不准在 Figma 里重画一份, 也不准在 React 里写第二套样式。
   - **Figma 端**: 用 `findOne(n => n.name === 'Button' && n.type === 'COMPONENT_SET')` 拿到现有 ComponentSet, 用 `.defaultVariant.createInstance()` 插入。设 `variantProperties` 切到目标 variant。**禁止用 figma.createComponent() 从零画一个看起来像 Button 的东西**。
   - **React 端**: 用 `import { Button } from '../Button/Button'` 然后渲染 `<Button variant="default">...</Button>`。**禁止在新组件的 module.css 里写一份 button 样式**。
   - **图标专项**: 任何"按钮里的 icon"、"输入框的 prefix icon"、"Header 的铃铛/菜单 icon" 都**必须**用 `<Icon name="..." />` (`src/components/Icon`) 或 Figma Icon ComponentSet 的 instance。**禁止画 svg / vector / Boolean 操作 / 占位 frame** (旧版"占位 frame 标 TODO" 的兜底也作废, 因 Icon 库已建好 88 个 icon)。
   - **判定法**: Phase 4/5 动手前, 看 `src/components/index.ts` 列出的已导出组件 + `src/components/Icon/icons/` 列出的 88 个 svg, 凡新组件用到这些都 instance/import。
   - **历史教训**: Header v1 初稿打算自画 "Education Hub" 按钮和 menu/bell 图标, 实际应该 instance `<Button variant="default" size="small">Education Hub</Button>` + `<Icon name="menu" />`, 否则一处改全不同步。

9. **🧩 复合组件按嵌套深度分 N 层做 (常见 1-3 层)**: 做 Breadcrumb / Tabs / Steps / Sidebar / Menu / Table 等**由更小单元嵌套组合**的组件时, 按视觉嵌套深度拆 N 层 ComponentSet, 从最小原子往上层层 instance 拼:
   - **Layer 1 (最小原子)**: 不可再分的最小可复用单元, 维度 = `State × 内部 prop` 穷尽变体
   - **Layer 2 ~ Layer N (逐级组合)**: 每层用上一层的 instance 拼成更大单元, 自己也是一个 ComponentSet, **绝不画裸图形 / 绝不 detach**。改 Layer K master → Layer K+1...N 全部自动同步
   - **图标必须 instance 现有 Icon 库** (Components/Icon/* 或 Icon/ ComponentSet), 不准在任何层画 svg / vector / Boolean 操作。没 Icon 库时用 14×14 占位 frame, 等 Icon 库建好再 swap

   **判定层数 — 看视觉嵌套深度**:

   | 组件 | Layer 1 (原子) | Layer 2 (中间) | Layer 3 (顶层) | 层数 |
   |------|----------------|----------------|----------------|------|
   | Button / Tag / Input / Avatar / Card | 自身 | — | — | **1** |
   | Breadcrumb | Link + Separator | Chain (Basic/WithIcon/...) | — | **2** |
   | Tabs | Tab + Indicator | Tab Bar | — | **2** |
   | Pagination | PageNum + Arrow + Ellipsis | Pager | — | **2** |
   | Steps | Step + Connector | Steps Strip | — | **2** |
   | **Sidebar Nav** | **Menu Item** | **Menu Group / 文件夹** | **Sidebar (Collapsed/Expanded)** | **3** |
   | Menu (带子菜单) | Menu Item | Sub-menu Group | Menu Root | **3** |
   | Table | Cell | Row | Table | **3** |
   | Tree | Node | Branch | Tree | **3** |
   | Layout 整页 | 子组件 | Header/Sider/Content/Footer | Page Layout | **3** |

   **判定问句 (动手前问 3 遍)**:
   1. 这一层是否还能拆出"反复出现的子单元"? 能 → 再向下抽一层
   2. 这一层的 instance 是否会在多种上层组合中复用? 能 → 必须独立 ComponentSet
   3. 改这一层 master 时, 上层是否能自动同步? 不能 → 中间有裸图形, 退回重做

   **黄金参照**:
   - 2 层范式: [Ant Design Breadcrumb](https://www.figma.com/design/qjJSplS9q3tDVIXyhRPVvN/Ant-Design-System?node-id=791-116) — Cell (Link+Separator) → Chain
   - 3 层范式: Ant Pro Layout Menu / Sidebar — Menu Item → Menu Group → Sidebar

   ⚠️ **旧版铁律错误警示** (2026-06-02 修正): 之前说"按旧库整体复刻不准拆原子" — **作废**。Shopee 旧库 Breadcrumb 的"4 个完整链"和 Sidebar 的"整张图"都是 Figma 早期没分层的产物, 修改成本极高。现按分层模式做, instance 引用一改全同步。

   ⚠️ **不要强行合并层** (常见错): 把 Sidebar 的 MenuItem + Group 合成一个大 ComponentSet 用 `groupSize=1/2/3/4` 维度区分 — 会爆变体且无法复用 Item。**正确做法**: MenuItem 独立 ComponentSet, Group 用 `Auto Layout + instance` 接受不定数量子项。

10. **🤔 Icon 引用不确定必须问, 严禁自画 (强化版 #8)**: 选 Icon 库里的 master 时, 凡是**不能 100% 确定**哪个 master 对应业务语义 (如 trigger 的 chevron / selected 的 check / item trailing 的占位 / clear 的 x 等), **必须先用 AskUserQuestion 问用户**, 给出 2-3 个候选 master ID + 视觉描述让用户拍板。**严禁猜测后画一个相似的 SVG 充当**。
    - **判定法**: Phase 4 起手前列「icon 清单」, 每项标:
      - ✅ 100% 明确 (例: status icon → 旧库 `success-s` 45:823)
      - ❓ 不确定 (例: dropdown trigger 用 arrow-down-s 还是 arrow-down? selected 用 success-s 还是仅文字变色?)
    - 凡 ❓ 项必须用 AskUserQuestion 让用户选, 通过后才动手
    - **历史教训**: Tabs Phase 4 我自画了 `image` / `question-mark` / `arrow-left` 3 个 icon 当占位, 后来全部要删 + 让用户加到 Icon 库再 instance, 双倍返工。Dropdown Phase 0 用户专门提醒了这条规则

11. **🎨 Icon 色 = semantic 色, 永远不用 border 色** (Alert 重做教训):
    - 视觉系统有 **三层**: bg (最浅) / border (中) / icon (深, semantic)。**不要混淆**。
    - **铁律**: status icon 用 `colorInfo` / `colorWarning` / `colorSuccess` / `colorError` (全局 semantic, 通常更深更饱和)。close / 通用 icon 用 `colorIcon` (通常 #999 灰)。**严禁用 `colorBorder*` 给 icon 上色**, 它们偏浅, 视觉上"灰扑扑"。
    - **判定法**: Phase 3 建 Alert/Toast/Modal 这类 status component 的 token 时, **必须分开 3 类色**:
      - `colorBg*` (浅, 用于背景)
      - `colorBorder*` (中, 用于边)
      - `colorIcon*` (深 semantic, 用于 icon) — **alias 到全局 `colorInfo/Warning/Success/Error`**, 别自己定义颜色
    - **历史教训**: Alert v1 我用 `colorBorderInfo` (#4EABF5 浅蓝) 给 info icon 上色, 实际应该用 `colorInfo` (#2673DD 深蓝). 4 个 status 全错, 用户指出后才修. 同时 close 没绑色, 留在 icon 库默认 #999 (碰巧对). 还有 Warning icon 是 `ELLIPSE + TEXT`, 我 fill override 只覆盖 `VECTOR/BOOLEAN_OPERATION`, ELLIPSE 漏掉 (见铁律 #15).

12. **🪙 每个视觉属性必须绑 token (Token Audit Checklist)** (Alert 重做教训):
    - **完成 Phase 4 后必须逐项自查**, 凡视觉表现的属性都得是 Variable 驱动, **不准硬编码任何数字 / 颜色**:
      - **几何**: `paddingTop / paddingBottom / paddingLeft / paddingRight / itemSpacing / cornerRadius (4 角) / strokeWeight`
      - **尺寸**: 所有 instance 的 `width` / `height` (icon / close button / avatar 等)
      - **字体**: 每个 TEXT 的 `fontSize` / `lineHeight` / `letterSpacing`
      - **颜色**: 每个 SOLID fill / stroke — bg / border / text / icon shape (每 type 都要), **包括 instance 内部的 vector shape**
    - **自查公式**: 写完后, 对每个 set 值的属性 ask 自己 "这值来自 Variable 吗?" 如果是硬编码 → 立刻补 token + bind.
    - **判定法**: Phase 4 完成后跑 `walk()` dump 所有 `boundVariables` 是否覆盖每个相关属性. 用 `figma.variables.setBoundVariableForPaint(paint, 'color', var)` 给 fill 上色; `node.setBoundVariable('paddingTop', var)` 给标量属性绑.
    - **历史教训**: Alert v1 我只绑了 bg/border fill, 留下 padding (硬编码 11/12/16) + fontSize / lineHeight / 字色 / icon size / corner radius 全部未绑. 后来用户指出要重绑 40 variants × 14 属性, 大批量返工.

13. **📊 变体穷举: 写 Cartesian Product 表后才动手** (Alert 重做教训):
    - Phase 2 时**必须列出 axes 的笛卡尔积**, 标记哪些是 valid / invalid 组合, 然后**按总数建 variants**, 不准为了"简洁"折叠 boolean 轴当 Component Property.
    - **判定法**: Phase 2 提案给用户时, 用表格写清:
      ```
      Status (4) × Layout (2) × HasIcon (2) × HasLink (2) × HasClose (2) = 64
      减去 invalid (Multi 强制 HasIcon=Yes / HasLink=No): -24
      Valid = 40
      ```
      然后建 40 个 variant. **绝不**用"Status 4 × Layout 2 = 8, 其他 boolean 走 Component Property" 这种偷工.
    - **何时可以走 Property 而非 variant**: 当某个 boolean 的 ON/OFF **不改变其他视觉属性** (e.g. 仅 show/hide 一个 slot) 时可以用 BOOLEAN Property. 但只要 ON/OFF 涉及 padding / alignment / 布局重排, 必须是 variant.
    - **历史教训**: Alert v1 我做了 Status 4 × Layout 2 = 8 variants, HasIcon/HasLink/HasClose 想用 BOOLEAN Property. 实际上每个 boolean 触发 padding 调整 (e.g. NoLink+NoClose → py-11 items-center, 有 link/close → py-12 items-start), 所以必须是 variant. 旧库实际 40 variants, 我做 8 = 漏 80%.

14. **🛑 Phase 4 完成必须截图给用户确认才能进 Phase 5** (Alert 重做教训):
    - 不再"自我感觉对就继续". Phase 4 (Figma) 跑完必须:
      1. 截 ComponentSet 全图 (40+ variants 一张)
      2. 截 Display 全图
      3. **明确问** "样式对吗? 有要调的告诉我, 我再开 Phase 5"
      4. 等用户回 "对" / "可以" / "继续" 才进 Phase 5
    - **禁止**: 在 Figma 完成同一回合就紧接着写 Alert.tsx / CSS / stories / Excel 等 (一次性把 Phase 4-6 全做完). 那样错了就大批量返工, 损耗 token 损耗用户耐心.
    - **判定法**: Phase 4 最后一个 use_figma call 之后, 必须 STOP, 截图 + 文字 prompt 用户确认. Phase 5 是 user-gated.
    - **历史教训**: Alert v1 我从 Phase 4 一路跑到 Phase 6 全部完成才截图给用户看. 用户指出"样式不对", 全部返工 (40 variants 重建 + Display 重做 + React 重写 + Excel 重登记). 耗时 = 直接做对的 3 倍.

15. **🎨 Icon 内部 shape 全 type 覆盖** (Alert 重做教训):
    - 给 icon instance 上色时, 不只是 `VECTOR` / `BOOLEAN_OPERATION`. Icon 内部可能有 `ELLIPSE` / `RECTANGLE` / `POLYGON` / `STAR` / `TEXT` (e.g. Warning notice-circle-s 是 `ELLIPSE (circle) + TEXT ("!" 白)`, success-s 是单个 `BOOLEAN_OPERATION`).
    - **铁律**: fill override 的 type filter 必须**至少**包含: `['ELLIPSE','VECTOR','BOOLEAN_OPERATION','RECTANGLE','POLYGON','STAR']`. 对于嵌套 TEXT (e.g. 数字 / "!"), **不要**自动 override (它们通常是反色, 如 Warning "!" 是白色), 只 override geometric shapes.
    - **判定法**: 给一个未知的 icon master 上色之前, 先 inspect 一遍:
      ```js
      const shapes = iconInst.findAll(n => n.type !== 'INSTANCE' && n.type !== 'FRAME');
      // 看清都有什么 type, 再写 fill loop
      ```
    - **历史教训**: Alert v1 我用 `findAll(n => n.type === 'VECTOR' || n.type === 'BOOLEAN_OPERATION')`, Warning icon (ELLIPSE + TEXT) 完全没被 hit, Warning icon 留在默认灰 #999. 用户截图给我看时发现 Warning icon 不黄, 这才知道. 现在 type filter 已扩到 6 类.

16. **📋 Property × Variant Inventory — Phase 2 不签字不进 Phase 3** (Filter 9 轮返工教训):

    Phase 2 输出**不能**只写 "Mode 2 × Count 3 = 6 variants" 这种概要句, **必须出完整 Inventory 表**, 每一格 (Property, Value) 组合都列, **且每格必须有 Figma URL**。没 URL 的格子 = ❓ 待补, **必须问用户**, 不准 AI 脑补外推。

    **Inventory 表格式** (必须用这个表跑 AskUserQuestion / preview 给用户审):

    | Property | Value | 视觉/行为 (一句话) | Figma URL | 子组件引用 | 状态 |
    |---|---|---|---|---|---|
    | Mode | Realtime | 没操作, 3-col grid | 1521:9569 | CascaderTrigger | ✅ 用户确认 |
    | Mode | Manual | 有操作 Apply/Reset | 1521:9570 | CascaderTrigger + Button | ✅ 用户确认 |
    | Count | 1 | 单 filter 占 1/3 row | 1521:9569#row1 | — | ✅ |
    | Count | 2 / 3 / 4 / 5 | (逐个列, 不准合并) | ... | — | ❓ / ✅ |

    **3 条强约束**:

    - **必须穷举每一格**: 写 "Count 1/2/3/4/5" 而非 "Count 多个 / Count ≥ 4 / etc."。不准用模糊量词。
    - **每格都要 URL**: "设计规范不全"不是脑补的理由。规范缺的格子 → 标 ❓ 在表里, 让用户补 URL。**用户补不出 URL 的格子 = 不在 scope 内, 删掉**。
    - **派生行为也算轴**: 同一个 Mode 下若有 2 套以上 layout (e.g. Filter Manual 内部 count≤3 flex / count≥4 grid), **必须**在 Inventory 表显式拆成多行, 不能藏在 React if-else 里, 否则 Phase 4 截图后用户会发现"咦还有一种长相", 大返工。

    **Inventory 表还要列**:

    - **子组件引用**: 业务方传入的 children 用哪个现有组件 (Input/Cascader/Dropdown/Button/...)。Storybook story 必须直接 import 真组件, **不准自画 styled button + Icon** 凑数 (Filter Storybook v1 用自画 button 替代下拉框, 用户后来要求重做)。
    - **Display 参考**: 跟哪个已建组件的 Display 排版作模板 (e.g. "照 Pagination Display 1388:215 4-col PVM")。Display 规范是统一的 (见铁律 #2), 不准自创布局。

    **判定法**: Phase 2 结尾 → Inventory 表用 `AskUserQuestion` (preview = 表格) 给用户审 → 用户对每格确认 (URL + 视觉描述都对) → 才进 Phase 2.5 Tier 评级 → 才进 Phase 3。**任何 ❓ 格不解决, 严禁进 Phase 3**。

    **历史教训**: Filter (2026-06-09) 9 轮返工根因 = Phase 2 锁的 scope = "Mode 2 × Count 3 (Collapsed/Expanded3/Expanded6) = 6 variants" — Count 值是我编的, "Collapsed/Expanded" 是我从"规范不全"脑补的, 实际应该是 "Mode 2 × Count 5 (1-5) = 10 variants" + Manual 内部 count≤3 flex / count≥4 grid 两套布局。用户每次甩新 reference URL 都要回头改, Token/ComponentSet/Display/React/Storybook 5 处级联翻工。如果 Phase 2 用 Inventory 表逐格 URL 确认, 后面 90% 的返工不会发生。

## Phase 1 理解（30 分钟）⭐⭐ Axis-First 数据结构

> 🔴 **本阶段的输出不是"散文报告", 而是一张结构化的「Axis Map 表」**。Axis Map 一路用到 Phase 2/4/5, 是整个流程的骨架。
> 🚨 **2026-06-03 改**: 旧版让 AI 自由"提取业务规则段落"导致 Phase 4 才被迫整理 axis, 中间反复返工 (见 Modal v1→v4 教训)。新版强制 Phase 1 就以 axis 思维记录。

### 🎯 核心理念 — Axis-First

**"变体 = 一个或多个 axis 的 value 组合"**。每读一个来源, 都问自己:

1. 这里展示的变化, 属于哪个 axis? (status / size / state / icon / shape / type / mode / ...)
2. 这个 axis 有哪些 value?
3. 这个变化是 **视觉变化**(影响 ComponentSet variant) 还是 **行为变化**(只影响 React prop)?

**绝不要**只记 "这个组件有 5 个视觉 symbol" — 那是结果, 不是数据结构。要把 5 个 symbol 反推回去成 axis × value。

### 1.1 读 Shopee 旧 Guidelines（提取 axis + Shopee 业务智慧）

**目的**：从「GP-{X}」frame 提取**视觉 axis** + Shopee 特有的设计约束。

**步骤**：

```javascript
await get_screenshot({
  fileKey: "ffIT3A1gHm5VAk6YUcbxiW",
  nodeId: "X:Y",        // GP-{X} frame
  maxDimension: 2500,
  enableBase64Response: true,
});
```

**提取(必须按 axis 结构记录)**：

- **类型汇总区**: 每个"业务类型" → 通常对应一个 `type` / `status` / `mode` axis 的一个 value
- **基本样式区**: 每个"状态" → `state` axis 的 value (Default/Hover/Active/Focus/Disabled)
- **视觉样式区**: 尺寸/字号/间距 数值 → 对应 `size` axis 的 value 或 token 数值
- **场景示例区**: Shopee 特有业务规则 (如 "Button 4 对齐方式" / "Modal 不嵌套") → **行为约束**, 不是 axis, 但要记下来给 Phase 6 usage.md 用

**忽略**：
- 旧的 8 类 / 10 类等繁琐分类 — 会被现代 axis 矩阵覆盖
- 老 Color 值 — 用 Shopee Tokens 替代
- 没 Token 化的尺寸 — 用新 Token 体系

### 1.2 读旧 Vue 组件源码（提取 axis 值 + props 命名）

**目的**：从旧 Vue props 反推 axis 名 + 找精确数值 (旧 Guidelines 给概念, 旧 Vue 给数字)。

**步骤**：

```bash
ls "/Users/.../Shopee前端组件源码/components/{x}/"
cat "Shopee前端组件源码/components/{x}/types/index.d.ts"   # props 类型定义 (axis 名 + values)
cat "Shopee前端组件源码/components/{x}/src/{x}.vue"        # 实现
cat "Shopee前端组件源码/components/{x}/src/box.vue"        # 看 SCSS 变量 (尺寸数值)
```

**提取(按 axis 整理)**：
- 旧 Vue 的 props 名 + 类型 → axis 名 + values (例: `size?: 'normal'|'medium'|'large'|'x-large'` = `size` axis, 4 values)
- SCSS 变量 → 数值 (例: `$normal-modal-width: 400px` = `size=normal` token = 400)
- 行为 prop (closeOnEsc / appendToBody / 等) → 单独列, 标 "behavior"

### 1.3 读旧组件库 (X9NSPXvdvwGkKTHs62QIMn) — Phase 4 起手必修

**目的**: 旧组件库 Figma 是**视觉真实源**。所有精确数值 (尺寸 / 颜色 / shadow / icon size / button label) 必须从这里扒, 不准凭旧 Vue SCSS 估算 (见 铁律 #6a)。

**步骤**: 用 `use_figma` 写 `walk()` dump 旧组件库 symbols 的 7 类数值, 同时**反推 axis**:

```javascript
const node = await figma.getNodeByIdAsync('<旧库 symbol id>');
function walk(n, d=0, max=5) {
  // dump: width/height/padding/cornerRadius/effects/font/fill/labels
}
return walk(node);
```

**反推 axis 法**: 旧组件库通常有 N 个 "symbol", 看每个 symbol 的视觉差异:
- 差异在 status icon 颜色 → 推出 `status` axis (success/error/warning/info)
- 差异在按钮数量/排列 → 推出 `buttons` axis (single/double)
- 差异在宽度 → 推出 `size` axis

**举例**: Modal 旧库 5 个 symbol 反推 axis:
| 旧库 symbol | 反推 axis 组合 |
|---|---|
| 普通提示弹窗 | `status=none + buttons=single` |
| 普通确认弹窗 | `status=none + buttons=double` |
| 含自定义辅助操作信息的弹窗 | `status=none + buttons=double + withAssist=yes` (withAssist 后期决定降级为 prop) |
| 带简单操作弹窗 | (children slot 内容差异, 非 axis, 是 prop 内容) |
| 带状态示意弹窗 | `status=success/error/warning/info + buttons=single/double` |

→ 提炼出 axis: `status` (5 values) + `buttons` (2 values) + `withAssist` (待决定)。

### 1.4 看新 System Test Figma 现状

**目的**: 已有 ComponentSet 直接读 variant 轴, 没有的话从 Phase 1.3 旧库结果起步。

### 🎯 Phase 1 输出 — Axis Map 表 ⭐ 必须产出

整个 Phase 1 唯一硬性产出物是这张表 (脑内 / note / 给用户看):

```
| Axis        | Values                              | 来源              | 类型      | 备注              |
|-------------|-------------------------------------|------------------|-----------|------------------|
| {axis_a}    | {v1} / {v2} / {v3}                  | 旧库 symbol N    | ✅ visual | 旧 Vue: {prop=...} |
| {axis_b}    | {v1} / {v2}                         | 旧 Vue prop      | ✅ visual | 旧库有视觉 +/-     |
```

**Shopee 业务规则附加**:
旧 Guidelines「场景示例」区的业务约束 (如 "Modal 不嵌 Modal" / "Button 同区域 ≤ 1 个 primary") 单独列, 不进 Axis Map, 给 Phase 6 .usage.md 决策树用。

## Phase 2 分析（15 分钟）⭐⭐ 分配每个 axis 三去向

**目的**: 拿 Phase 1 输出的 Axis Map 表, 给每个 axis 分配明确去向 (ComponentSet variant / prop only / 两者都进), 不再"自由决定变体维度"。

### 2.1 三去向分配规则

对 Phase 1 Axis Map 的每一行 axis, 按下面规则分配:

| Axis 类型 | 去向 | 例子 | Storybook ArgTypes |
|---|---|---|---|
| ✅ visual + 离散值 (≤ 6 values) + 笛卡尔积 ≤ 20 | **ComponentSet variant 轴** | Modal `status` (5 values), Button `type` (5 values) | enum select |
| ✅ visual + 离散值 (≤ 6) **但加入会爆变体** | **React prop only** (不进 ComponentSet, 业务运行时控) | Modal `size` (4 values, 加入 = 5×2×4 = 40 变体, 爆) → 用 width prop | enum select |
| ✅ visual + 连续值 / 数量 > 6 | **React prop only** | `width` 自定义 / `maxItems` 数字 | number |
| ⚠️ behavior + 视觉影响小 | **React prop only** | `withAssist` slot / `showClose` boolean | boolean |
| 🎯 pure behavior | **React prop only** (必然) | `closeOnEsc` / `onConfirm` | callback |

**决策铁律**:
- **ComponentSet variant 笛卡尔积上限 = 20**。超过就强制把次要 axis 降级为 prop
- 一个 axis 只能去一个地方, **不允许 variant 轴跟 prop 同时存在** (那样改一处不同步)
- 行为 axis 永远只是 prop, 不进 variant
- 不准引入 Phase 1 Axis Map **没有的新 axis** — 那就是 Tier 4 凭空创造, 必须用户签字

### 2.2 输出 Axis 决策表

把 Phase 1 Axis Map 加一列 "去向"+ "Baseline":

```
| Axis        | Values            | 类型        | 去向        | Baseline | Tier |
|-------------|-------------------|-------------|-------------|----------|------|
| status      | none/success/error/warning/info | ✅ visual | variant 轴 1 | none     | T2   |
| buttons     | single/double     | ✅ visual   | variant 轴 2 | single   | T2   |
| size        | normal/medium/large/x-large | ✅ visual | prop only   | normal   | T2   |
| withAssist  | no/yes            | ⚠️ behavior | prop only   | no       | T2   |
| closeOnEsc  | no/yes            | 🎯 pure     | prop only   | no       | T2   |
| confirmText | 任意字符串         | 🎯 pure     | prop only   | "Confirm"| T2   |
```

**Baseline 定义**: 该 axis 的 "默认值", 用于 Property × Value Matrix Display 里非该行的所有其它 axis 保持的值。**通常选最常用 / 最素净的 value** (status=none / size=normal / 等)。

### 2.3 列 Token 需求 (按 axis 推)

每个 visual axis 的 N 个 value × 它需要的 token 类型 = token 数量:

- `status` (5 values) × 4 status colors → 4 个 Global color tokens (none 不要色)
- `size` (4 values) × 1 width → 4 个 Component dimension tokens
- `state` (5 values) × 2 (bg + fg) → 10 个 Global color tokens

**Component-specific Tokens** (组件独有): 命名 `Components/{X}/Component/{tokenName}`, 例: `paddingInline` / `borderRadius`
**Global Aliases** (指向语义层): 命名 `Components/{X}/Global/{tokenName}`, 例: `colorBg → colorBgElevated`

参考 Button 的 54 token / Modal 的 34 token 量级, **同等规模组件大概也是这个量级**。

### 2.4 输出"实施计划"

用 `AskUserQuestion` 给用户看 (3 张表):

- **Axis 决策表** (2.2 输出) — 用户验证 axis 分配是否合理
- **Token 需求清单** (2.3 输出) — 用户验证 token 数量是否合理
- **预估笛卡尔积** = variant 轴 values 数相乘 (上限 20)

**用户确认后再下一步。** 不确认别动手。

## Phase 2.5 Scope 契约（15 分钟）⭐ 防越界关键步 — **必须先过 2.5.0 Inventory, 再做 2.5.1 Tier**

> 🚨 **Why 加这一步**: AI 在做组件时会无意识地从训练数据(Ant Design / Material UI / Bootstrap 等)套用"常见"特性, 但这些特性可能根本不在 Shopee 体系内。例如 Tag 加 `icon`/`closable`、Card 加 `extra`/`footer` slot —— Figma 和旧 Vue 都没有, 是 AI 自己脑补的。
>
> 🎯 **核心规则（必须背下来）**:
> **"样式只能来自旧规范或旧组件库，你不能创造全新的。但旧规范或库中缺少的状态，你可以补齐，比如旧的里面只有 default 状态，你可以补全 hover、disabled 状态等。"**

### 2.5.0 Property × Variant Inventory 表 (新增 — 见铁律 #16)

> **顺序铁律**: 2.5.0 Inventory **先**做 → 拿到用户对每格 URL 的确认 → **再**做 2.5.1 Tier 评级 → 再进 Phase 3。**任何 ❓ 格未补 URL, 不准进入下一步**。

不再用 "Mode 2 × Count 3 = 6 variants" 这种概要句锁 scope, 改用**完整 Inventory 表**, 逐格 (Property, Value) + Figma URL:

| Property | Value | 视觉/行为 (一句话) | Figma URL | 子组件引用 | 状态 |
|---|---|---|---|---|---|
| Status | none / success / error / warning / info | 4 色调 + 默认无图标 | 旧库 246:32 sub-frame | Icon ComponentSet | ✅ / ❓ |
| Layout | inline / multi-line | 单行 / 多行包裹 | 旧库 246:32 row 2 | — | ✅ / ❓ |
| HasIcon | yes / no | 左侧带 status icon | 旧库 246:32 row 3 | Icon | ✅ / ❓ |
| ... | (逐个列, 不准合并) | ... | ... | ... | ❓ / ✅ |

**3 条强约束**:

- **必须穷举每一格**: 写每个 axis 的具体 value, 不准 "etc." / "多个" / "≥4"。
- **每格都要 URL**: 用户给不出 URL 的格子 = 不在 scope, 删掉。**严禁 AI 用"设计规范不全"为理由脑补外推**。
- **派生 layout 也算轴**: 同一 axis value 下有 2 套以上视觉 (Filter Manual count≤3 vs count≥4) 必须显式拆行, 不能藏在实现里。

**Inventory 表还要列**:

- **子组件引用**: 这一格如果含 children, 用哪个现有组件 (Input/Dropdown/Cascader/Button/...)。
- **Display 参考**: 跟哪个已建组件的 Display 排版作模板 (默认照最近一个 Phase 4 完成的 Display)。

**落地动作**:

1. Inventory 表用 `AskUserQuestion` (preview = 表格) 给用户审
2. 用户对每格逐一回 "✅ 确认 + URL 对" 或 "❓ 补 URL / 删此格"
3. **所有格都是 ✅** 才能进 2.5.1 Tier 评级
4. 任何 ❓ 留着的 axis value → 在 .types.ts / .usage.md 里都不存在

### 3.1 在 Figma 创建 Component Tokens

```javascript
// 用 use_figma 批量创建 (不算 API 配额!)
await use_figma({
  fileKey: "KTvcllui6OGgNPI5f1DfHe",
  skillNames: "figma-use",
  code: `
    const coll = (await figma.variables.getLocalVariableCollectionsAsync())[0];
    const modeId = coll.modes[0].modeId;
    const allVars = await figma.variables.getLocalVariablesAsync();
    const byName = {};
    for (const v of allVars) byName[v.name] = v;

    function alias(name) {
      const t = byName[name];
      return t ? { type: 'VARIABLE_ALIAS', id: t.id } : null;
    }
    function add(name, type, scopes, target) {
      if (byName[name]) return;
      const v = figma.variables.createVariable(name, coll, type);
      v.scopes = scopes;
      const val = (typeof target === 'string') ? alias(target) : target;
      v.setValueForMode(modeId, val);
      byName[name] = v;
    }

    // Component 层
    add('Components/${X}/Component/xxx', 'COLOR', ['FRAME_FILL'], 'Colors/...');
    // ... 把所有 Component 层 token 加完

    // Global 层
    add('Components/${X}/Global/colorBg', 'COLOR', ['FRAME_FILL'], 'Colors/Neutral/Bg/colorBgContainer');
    // ... 把所有 Global 层 token 加完

    return { created: Object.keys(byName).length };
  `
});
```

### 4.0 ⭐ 复合组件预判 + 分层建法 (N 层通用, 常见 1-3 层)

> 单元素组件 (Button / Tag / Card / Input / Avatar) → **跳过本节, 直接 4.1**
> 复合组件 (Breadcrumb / Tabs / Steps / Pagination / Sidebar / Menu / Table) → **必须按本节分层做**

#### 4.0.1 判定层数 (动手前 5 分钟)

按上方铁律 #8 表格判定层数 (1 / 2 / 3 / ...), 然后回答这 3 个问题决定每层的拆法:

1. **Layer 1 (最小原子) 是什么?** 不可再分的最小可复用单元, 维度 = `State × 内部 prop` 穷尽
   - 2 层例 (Breadcrumb): Link (State×Icon×Label) + Separator (单 variant)
   - 3 层例 (Sidebar): Menu Item (State×Icon×Level×HasArrow×Selected 等)
2. **中间层 (Layer 2 ~ N-1) 用什么方式聚合下层?** Auto Layout 横排 / 纵排 / Grid
   - Breadcrumb 没有中间层 (2 层) → Layer 2 直接是 chain
   - Sidebar 中间层 = Menu Group/文件夹, 纵排 1 个 title + N 个 MenuItem instance
3. **顶层 (Layer N) 提供哪些 Type variant?** 几种典型用法
   - Breadcrumb: Basic / WithIcon / WithDropdown
   - Sidebar: Collapsed / Expanded
   - Tabs: Line / Card / Segmented

#### 4.0.2 核心铁律: 每一层 K 的 variant 内部 100% 用 Layer K-1 的 instance 拼

不准画裸图形, 不准 detach。改 Layer K master → K+1...N 自动同步。

通用代码模板 (适用 N=2 / 3 / 更多):

```javascript
await use_figma({
  fileKey: 'KTvcllui6OGgNPI5f1DfHe',
  code: `

    // - 文字 Roboto Regular (按 Phase 1 旧库实际字重, 不脑补)
    // - 颜色/间距/字号/圆角全 setBoundVariable
    // - icon 一律 instance Icon 库, 0 个 svg/vector 节点
    const atomVariants = STATE_MATRIX.map(s => buildAtomVariant(s));
    const layer1 = figma.combineAsVariants(atomVariants, page);
    layer1.name = '{Atom Name}';     // 如 'Breadcrumb Link' / 'Menu Item'
    layer1.primaryAxisSizingMode = 'AUTO';
    layer1.counterAxisSizingMode = 'AUTO';

    // ============ Layer 2: 中间组合 (若 N≥3 才需要) ============
    // 用 Layer 1 的 defaultVariant.createInstance() 拼
    const atomDefault = layer1.defaultVariant;
    const groupVariants = GROUP_TYPES.map(t => {
      const v = figma.createComponent();
      v.name = 'Type=' + t;
      v.layoutMode = 'VERTICAL';   // Sidebar 是纵排, 按组件调整
      v.primaryAxisSizingMode = 'AUTO';
      v.counterAxisSizingMode = 'AUTO';
      // 装 title (若有) + 3-5 个 atomDefault.createInstance()
      // 末位 instance.setProperties({State: 'XXX'}) 切到"末位/激活"态
      return v;
    });
    const layer2 = figma.combineAsVariants(groupVariants, page);
    layer2.name = '{Group Name}';    // 如 'Menu Group'

    // ============ Layer N: 顶层 (Type 维度列典型用法) ============
    // 用 Layer N-1 的 instance 拼
    const upstream = (layer2 || layer1).defaultVariant;
    const topVariants = TOP_TYPES.map(t => {
      const v = figma.createComponent();
      v.name = 'Type=' + t;
      v.layoutMode = 'VERTICAL';   // 或 HORIZONTAL, 按组件
      // 装 N 个 upstream.createInstance()
      return v;
    });
    const layerN = figma.combineAsVariants(topVariants, page);
    layerN.name = '{Component Name}';   // 如 'Breadcrumb' / 'Sidebar'
  `
});
```

**每层必检** (适用 Layer 1 ~ N):
- [ ] 该层 ComponentSet 已建, 维度穷尽
- [ ] **该层内部 0 个裸图形** (用 `figma.root.findAll(n => n.type === 'VECTOR')` 自查 — Layer 2/3/N 应该没有任何 vector 节点, 所有视觉来自下一层 instance + Icon 库 instance)
- [ ] icon 全部 instance Icon 库 ComponentSet
- [ ] 颜色 / 间距 / 字号 / 圆角全 `setBoundVariable`
- [ ] 上一层的 `defaultVariant` 已正确选中, 不要 instance 错变体
- [ ] 末位 / 激活态 已用 `instance.setProperties()` 切对

#### 4.0.3 Display 排版 (复合组件 — 每层一个独立 Display)

⚠️ **2026-06-03 改**: 复合组件的 Display **不再把 Layer 1/2/N 塞同一个 Display frame**, 而是**每个 Layer 1 atom 单建 Display + Layer 2 root 单建 Display**。每个 Display 内部都是单一 Property × Value Matrix (见后面专节)。

```
{X}.Item — Display          ← Layer 1 atom 的 props 矩阵 (自己的 prop 轴, 不含 Layer 2 维度)
{X} — Display               ← Layer 2 root 的 props 矩阵 (Type / 自定义 props, 不重复展示 Layer 1)
```

**禁止做法**: 老版把 Layer 1 atoms + Layer 2 root + Scenarios 塞一个超长 Display — 设计师 review 时分不清"我现在在评估哪个 ComponentSet"。

按 4.1 Step 2 + 「📐 Display 排版统一规范」做。

#### 4.0.4 复合组件易踩坑

- ❌ **跳过中间层** (Sidebar 直接 MenuItem instance 装到 Sidebar 里, 跳过 Group/文件夹) → 想给 Group 加 title 就得 detach 改, 后期一处改 N 处
- ❌ **上层用裸图形假装是 instance** → 改下层 master 不同步, 直接 KO。Layer 2/3/N 应该 0 个 vector 节点
- ❌ **icon 在任何层画 svg** → 违反铁律 #8。即使旧库是 svg, 也要先找 Icon 库, 没有就占位 frame 标 TODO
- ❌ **最小原子的 State 维度漏"末位/激活"态** → 上层组合时末位 instance 没 variant 可切。常见末位态: Breadcrumb=Current, Steps=Process, Tabs=Active, Menu/Sidebar=Selected
- ❌ **强行合并层省事** (Sidebar "4 group × 5 item = 20 项硬画大 ComponentSet") → 变体爆炸, 业务想加一项就得重画
- ❌ **分隔/连接元素不 ComponentSet 化** (Separator 做成 Link 自带的 ::after / Connector 画进 Step 里) → 不能 swap, 不能换符号
- ❌ **不同层用同名 ComponentSet** (Layer 1 叫 'Menu' Layer 3 也叫 'Menu') → 找 ComponentSet 时易拿错。统一命名: `{原子名}` / `{组名} Group` / `{组件名}`

### 🟧 矩阵表格细则

| 项 | 规范 |
|---|---|
| **行 (Row)** | **每行 = 一个 prop 轴** (Type / Size / Shape / Icon / State / 自定义 props) |
| **列 (Column)** | 该 prop 的所有 value 横排, 一个 value 一格 |
| **第 1 列** | Property label + "N values" 副标 (顶左) |
| **后续列** | UPPER value 标签 (顶) + ComponentSet instance (下) |
| **空格子** | 当该 prop 的 value 数 < 表格最大列数时, 后面格子**留空** (不画 placeholder, 不画虚线) |
| **baseline** | 除当前行变化的那个 prop 之外, 其它 prop **必须保持 default 值**, 这样能隔离单个 prop 的变化 |
| **必须 instance** | 每个 cell 必须是 `variant.createInstance()`, **绝不能画裸图形**。改 ComponentSet master → 矩阵全跟着更新 |
| **统一对齐** | **所有 cell 都 top-left**: `primaryAxisAlignItems='MIN'`, `counterAxisAlignItems='MIN'`, padding 20 |
| **Property label 字体** | 14 Semi Bold + 11 Regular "N values" 副标 |
| **Value label 字体** | 11 Medium UPPER letter-spacing 0.5 (`colorTextSecondary`) |
| **🆕 等高 (within row)** | 行内所有 cell **高度等高**, 自适应该行最高 cell 的内容. Figma 设法: row `counterAxisSizingMode='AUTO'` (HUG 到最高), 每 cell `layoutSizingVertical='FILL'`. **禁止给 cell 设 FIXED 高度**, 否则 padding 多了显空白. |
| **🆕 等宽 (within row)** | 行内所有 cell **宽度等宽**, FILL 行宽度均分. Figma 设法: row `layoutSizingHorizontal='FILL'` (FILL 父表格宽), 每 cell `layoutSizingHorizontal='FILL'`. **禁止给 cell 设 FIXED 宽度** (200/220/...), 让 row 内 cell 数决定. |
| **🆕 列对齐 (across rows)** | 因为每行都"FILL row 宽度均分", 所有行的 cell 数相同时**自动列对齐**. 不同行 cell 数不同时**右侧留空** (cells 数 < max), 不补 placeholder. |

**为什么用 Property × Value 而不是笛卡尔积矩阵**:
- 笛卡尔积 (旧版 Mode A) 在 5 维变体时爆炸到 450+ cell, 设计师扫不动
- 真实 review 场景 99% 是 "想看 `Shape=Round` 长啥样" / "想看 `State=Hover` 颜色对不对" — 只关心一个 prop
- Property × Value: N 个 prop = N 行, max 列数 = 该组件最大 value count (一般 ≤ 6), 一屏看完整个 design surface

**为什么 baseline 其它 prop default**:
- 隔离: Type 行的 Hover 看不到, 因为 Hover 是 State 维度, 不该跟 Type 混; 想看 Type=Primary+State=Hover 直接看 State 行 col 2
- 一致: 所有行第 1 个 cell 视觉相同 (Type=Primary+Size=Default+...) — 横向比较"哪行哪列偏离基线"一目了然

### 🚫 禁用做法

- ❌ 加 "Section / Scenarios" 业务场景段 — Display 不讲故事
- ❌ 加 "Layer 1 — Atoms" / "Layer 2 — Composition" 分层段 (复合组件) — Display 只看根 ComponentSet 的 prop 矩阵, Layer 1 cell 各自独立 Display
- ❌ Header / Footer 用不同灰色 — Section/Footer 全白, **只有 Header 深色**
- ❌ Cell 内容 vertical center — 必须 top-left
- ❌ Cell 内容居中 (老 Mode A "左对齐 + counter CENTER") — 全部改顶左
- ❌ 中文 label ("属性" / "样式 1" / "变体") — 全英文 (Property / Variant N / value name)
- ❌ 表格里画 placeholder ("—" / 灰框) 占满空列 — 空就空着

### 🧩 复合组件 (Layer 1 + Layer 2) 怎么 Display

按 Layer 拆 **N 个独立 Display frame**, 每个 frame 内部还是单一 Property × Value Matrix:
- `{X}.Item — Display` (Layer 1 atom): 这个原子的 props 矩阵
- `{X} — Display` (Layer 2 root): root 自己的 props 矩阵 (Type / 自定义 props)

⚠️ **不准把 Layer 1 atoms 塞到 Layer 2 的 Display 里**(老做法), 那样混淆"现在我在 review 哪个组件"。

### 📋 Storybook 怎么对齐 (PropMatrix story)

Storybook .stories.tsx 必须有一个 `PropMatrix` story, **跟 Figma Display 同结构**:

```tsx

  render: () => (

      component={Button}
      baseline={{ variant: 'primary', size: 'default', shape: 'default', iconPosition: 'left' }}
```

其它业务场景 stories (Form 用 / 确认弹窗 用 / 详情页用 ...) 也留在 .stories.tsx, 但**不进 Figma Display**。Figma 是设计 surface, Storybook 是 dev 文档, 分工清楚。

### 🚨 七大易踩坑 (实战踩过的, 一次都不准再犯)

1. **跳 Phase 4 直接写代码** ← Radio 第一版犯过。理由"设计师手动建"是过时的，**AI 就是来辅助做这步的**。
2. **Display 用裸图形画** ← Radio 第一版也犯过。必须用 ComponentSet 的 `createInstance()`，不然 token 改了不同步。
3. **Display 排版随便发挥** ← 必须严格按「📐 Display 排版统一规范」(2026-06-03 改: Property × Value Matrix) 做：深色 #1B1B1F Header + 单一矩阵 + 每行一个 prop + 全英文 + cell 顶左对齐, **不放 Scenarios, 不分 Mode A/B/C**。
4. **把 Tier 1 状态当成 Tier 4 让用户选** ← Checkbox 第一版犯过。`indeterminate` 在旧 Guidelines + 旧 Vue 都有, 是组件的标准状态, 我却放到 AskUserQuestion 里"要不要做" → 用户选了"不要" → 漏画 2 个变体, 要回头补救。**判定方法**: 用上方「Tier 评级速查」表对每个 prop / 状态打分, **旧规范 + 旧 Vue 都有的 (Tier 1) 直接默认做, 不问用户**。
5. **Phase 1 看截图不仔细** ← 旧 Guidelines GP-{X} 的"基本样式"表格里**每一行都是一个状态**, 包括 Normal/Hover/Selected/**Indeterminate**/Disabled/Focus 等。看的时候要逐行数, 数到几个 = ComponentSet 至少要做几个变体, 不准遗漏。
6. **把运行时动效当 Figma variant 画** ← Switch 第一版犯过。Loading / Spin / Animation 这类**靠时序变化**的状态, Figma 是静态画板**画不出动效**, 强行画静态帧只会画出"看起来像 X 但又不是 X"的怪图. **规则**: 运行时动效**只在代码里实现**, Figma 完全不画 variant, Display 也不展示。
7. **Phase 1 只数"状态"忘了数"类型"** ← Switch 第一版犯过。旧 Guidelines 经常有两张表: "**类型汇总**" (业务变体, 如 Switch "普通开关" + "**带文字开关**") + "**基本样式**" (交互状态, Normal/Hover/Disabled). 第一版我只数了基本样式的状态, 把"带文字开关"这个**业务变体**整个漏了, 即使后面建 Token 时用到了 `colorInnerText` 也没意识到该补对应变体。

### 🚫 不画 Figma variant 的状态清单 (代码实现就行)

⚠️ **细化规则 (Badge Pulse 教训)**: 是否画 variant **看的是"视觉是否有独立辨识度"**, 不是"是否有动画"。两种情况:

#### 情况 A — **完全不画 variant** (动画过程本身就是视觉)
- **Loading** (旋转 spinner — 静止帧只是个开口环, 没有"Loading 感")
- **Skeleton Shimmer** (闪动本身就是表达"加载中", 静止灰条没意义)
- **Toast 入场/出场** (slide-in 动画, 终态等于普通 Toast)
- **Click Ripple** (按下扩散, 静止帧只是个圆)
- **Hover transition** (过渡本身, 不画过渡的中间帧; **Hover 终态色仍要画**)

#### 情况 B — **画静止帧 variant + 代码加动画** (静止帧本身有辨识度)
- **Pulse 呼吸灯** (外圈半透明 + 内点实心的"双圈"结构本身就是辨识) → Figma 画静止帧, CSS 加 scale+opacity 循环
- **Indeterminate Progress** (一段进度条本身有辨识) → Figma 画静止帧, CSS 加滑动动画
- **Heartbeat icon** (心形本身有辨识) → Figma 画静止帧, CSS 加 scale 循环

#### 怎么判定?

问自己: **"不带动画时, 这个东西光看视觉能不能认出来是什么?"**
- 能 → 情况 B, 画静止帧 variant
- 不能 (必须靠动画才表达语义) → 情况 A, 完全不画

**实例对照表**:

| 状态 | 视觉辨识度 (静止帧) | 决策 |
|---|---|---|
| Switch Loading 转圈 | 开口圆环 — 看不懂 | ❌ 不画 variant |
| Badge Pulse 呼吸灯 | 双圈结构 — 看得懂 | ✅ 画静止帧 variant |
| Button Loading 转圈 | 开口圆环 — 看不懂 | ❌ 不画 variant |
| Skeleton Shimmer | 灰条 — 看不出 Loading | ❌ 不画 variant |
| Progress 不定态 | 一段进度条 — 能看懂 | ✅ 画静止帧 variant |

**实现侧**: 不论是否画 variant, **动画一律 Phase 5 用 CSS animation / Web Animations API 实现**。

### 📐 文字/图标在组件内的精确数值: 必须从旧库扒, 不准估算

Switch 第一版我估算了"on"/"off" 内部文字的位置 (`text.x = sizeSpec.width - text.width - sizeSpec.labelPad`), 结果 Small 尺寸的文字被 dot 完全遮挡. 旧库的实际数值是:

| 项 | 旧库精确值 | 我估算的错值 |
|---|---|---|
| 字体 | **Roboto Regular** | Inter Medium ❌ |
| 字号 | **12px** | 10px (Small) / 12px (Default) ❌ |
| 大小写 | **小写 "on"/"off"** | 大写 "On"/"Off" ❌ |
| 位置 (Default On) | x=**7** y=**4** | 公式估算 ❌ |
| 位置 (Default Off) | x=**25** y=**5** | 公式估算 ❌ |
| Small 文字版 | **不存在** (16px 高放不下) | 强行加, 导致遮挡 ❌ |

**规则**: 凡是涉及 `字体 / 字号 / xy 坐标 / cornerRadius / strokeWeight / 颜色具体值` 这些**精确数值**, 必须先去旧库 `get_node_by_id` + `walk()` **扒出实际数值**, 不准凭"应该是这样吧"估算。

**做法**: Phase 1 读旧库时, 对带文字 / 带图标 / 复杂内部结构的变体, 用 `use_figma` 写一个 `walk()` 函数把所有节点的 `width / height / x / y / fontSize / fontName / characters / cornerRadius` 全量 dump 出来, 抄到 Phase 4 的代码里。

### 🎲 ComponentSet 笛卡尔积可以有空洞 (语义合理就允许)

Switch 第一版我把 Size × State × Label = 28 全做了, 包括 Small × OnOff, 结果 Small 根本放不下文字 → 强画 → 被 dot 遮挡。

**规则**: ComponentSet 不要求笛卡尔积**全满**, 当某些组合**语义上不存在**时, 直接在 ComponentSet 里不建那个变体即可 (Figma 允许空洞)。比如:
- Switch: `Size=Small × Label=OnOff` 不存在 (16px 高放不下)
- Button: `Type=Link × isLoading=true` 可能不存在 (Link 没 loading 概念)
- Input: `Type=textarea × Suffix=Icon` 可能不存在

**做法**: Phase 2 画维度矩阵时, 对每个组合问"这个组合在旧库存在吗 / 语义上有意义吗", 不存在的直接标 "—" 不建。Display 矩阵里对应 cell 渲染 "—" 即可。

**警示**：写文档时**一定要**用 `get_screenshot` 把旧 Guidelines 的 {X} 章节看一遍，提取 Shopee 特有规则，而不是脑补。
